# 长期目标调度 P0 事故：第一阶段根因分析

> **这份文档记录什么**：2026-10-26 → 2027-07-01「每天背考研英语单词」被错误拆成
> 7 个「第1天…第7天」且全部排进同一天的事故，对应的真实数据流、根因定位、
> 责任分层（prompt / schema / scheduler / API / frontend）和最小修复方案。
>
> **怎么使用**：先读第 1～4 节理解事故是怎么发生的；第 5～7 节按责任层定位问题；
> 第 8～11 节是实施与验收依据。第二阶段的代码改动和测试结果见同目录
> `LONG_TERM_SCHEDULING_FIX_REPORT.md`。
>
> **调查原则**：先追数据流和数据结构，再改代码；不通过增加 prompt 文案掩盖
> scheduler / schema / horizon 的结构问题；LLM 只负责语义分类和「做什么」，
> 日期枚举、边界、容量、落库全部由 deterministic code 负责。

### 1.1 Goal 数据结构：长期语义是否真的存在？

**结论：日期字段已经存在，但「目标类型 / 重复语义」没有被可靠地机器化。**

- `GoalInput`（`app/agent/state.py:110`）已经有：
  `goal_type`, `deadline`, `start_date`, `task_kind`, `daily_target_minutes`,
  `recurrence_weekdays`, `target_amount`, `target_unit`。
- `/goals` CRUD（`app/schemas/goal.py:43`）与 `goals` ORM
  （`app/infrastructure/database/models/goal.py:40-48`）也都已经落了这些列。
- 迁移 `alembic/versions/d0853f9e14b4_task_kinds_and_occurrence_series.py`
  已经创建了 `goals.start_date / task_kind / daily_target_minutes /
  recurrence_weekdays / target_*` 与 `tasks.task_kind / series_id /
  series_index / occurrence_date / target_*`。

所以「数据库里没有长期字段」**不是**根因。真正的问题是：

1. `task_kind` 在 API 层是可选、无默认、无归一化的
   （`app/schemas/plan.py:41`、`app/schemas/goal.py:55`）。
2. `goal_type` 在 `/goals` 默认 `OTHER`（`app/schemas/goal.py:46`），
   在 `/plans/generate` 默认 `SHORT_TERM`（`app/schemas/plan.py:33`）。
3. `/plans/decompose` 的 `DecomposeGoal` 根本没有 `goal_type`
   （`app/schemas/plan.py:183`），`_decompose_request` 也不转发它
   （`app/api/v1/plans.py:121`）。前端实际走 `/plans/preview`，
   但这也说明「长期」语义在请求链路上并不稳定。
4. 最关键：**LLM 的 `goal_analysis` 结果没有重复语义字段**。
   `AnalyzedGoal` 只有 `objective / subtasks / constraints`
   （`app/agent/schemas.py:36`）。「每天」只能变成一条自然语言 constraint，
   无法进入 deterministic 的日期展开逻辑。

### 1.2 GoalAnalysisResult：能否表达 ONE_OFF / RECURRING / PROJECT？

**不能。** 当前 schema（`app/agent/schemas.py:36-49`）没有：

- `goal_kind` / `scheduling_mode`
- `recurrence.frequency`
- `recurrence.interval`
- `recurrence.weekdays`
- `work_units`（课程型目标的有限工作单元）

因此：

```
用户说「每天背单词」
  -> goal_analysis 只能写 constraints: ["每天"]   (自然语言)
  -> plan_generation 没有任何机器可读的 repeated 信号
  -> deterministic 层无法知道该按天展开
```

### 1.3 PlanGenerationResult / TaskDraft：区分能力

`GeneratedTaskDraft`（`app/agent/schemas.py:108`）已经有：

- `task_kind: TaskKind`（`one_off / long_term / routine`）
- `series_id`, `series_index`
- `occurrence_date`
- `target_amount`, `target_unit`

`PlanGenerationResult` 还有 `start_date / end_date`。

**能表达「series 实例」和「一次性工作单元」，但不能表达「recurrence template」，
也没有 `PROJECT`（有限课程/项目）的独立语义。** `TaskKind.LONG_TERM` 目前被
`_infer_task_kind` 直接映射成「每天复制」（`plan_drafter.py:51-61`），
这正是把「学完高等数学」错误日复一日的结构性原因。

「第1天、第2天……」当前只存在于 **`title` 文本**里（LLM 生成），
不在任何日期字段。`scheduler` 只读：
`task_earliest_dates`（来自 `occurrence_date`）与 `task_deadlines`
（来自 `draft.deadline`）（`app/agent/nodes/_shared.py:172-182`、
`app/domain/scheduling/scheduler.py:219-227`）。**scheduler 不会解析 title。**

### 1.4 Scheduler：为什么同一天、为什么只有一周

`scheduler.py` 的真实逻辑：

- horizon：`start = context.today or today`；
  `end = start + DEFAULT_HORIZON_DAYS(13)`，再被 `task_deadlines` 的最大值撑大
  （`scheduler.py:82-101`）。
- 每个 task 从 `max(start_date, task_earliest_dates[id])` 开始逐日扫描，
  找第一个满足容量/缓冲区/HIGH 间隔/固定事件的位置
  （`scheduler.py:201-248`）。
- 没有 `occurrence_date` 的任务，`earliest = start_date`（今天），
  因此只要有容量，就会被塞进**第一个可行日**。

所以：

- **「第1～7天全部同一天」** = 这 7 个 draft 根本没有 `occurrence_date` /
  `deadline`，被当成 7 个普通 one-off；scheduler 从今天开始贪心放置，
  20 分钟 × 7 = 140 分钟 < 300 分钟日容量，全部落在 10-26。
- **「只有一周」** = 不是 scheduler 只排 7 天，而是**只生成了 7 个 draft**。
  后端没有 7 天常量；`DEFAULT_HORIZON_DAYS = 13`（`app/domain/scheduling/constants.py:7`）。
  7 来自 LLM 自己按「一周」枚举了「第1天…第7天」。
- `scheduler` 当前处理的是 **task occurrence**（它假定输入已经是实例），
  不是 **task template**；它不知道 goal 的 start_date / end_date / recurrence。

### 1.5 API / Frontend：一周后没有任务，是谁造成的？

| 层 | 结论 | 证据 |
|---|---|---|
| 后端生成 | **没有生成一周后的任务** | `plan_drafter` 的展开是条件性的；未触发时只有 LLM 返回的 7 个 draft |
| 数据库 | **只存了实际生成的 draft** | `_persist_final_plan` 只写 `final.tasks`（`plan_service.py:973-1018`） |
| API 查询 | **没有 7 天过滤** | `GET /plans/{id}` → `list_by_plan` 返回全部未删除任务（`task_repository.py:84-90`） |
| 前端展示 | **只渲染今天 + 当前自然周（周一～周日）** | `new_frontend/src/app/index.tsx:254-264,562-592`；月视图是占位（`index.tsx:594-601`） |
| lazy materialization | **不存在** | 全仓库没有按 rolling horizon 生成 occurrence 的逻辑；`materialize` 只命中导入的固定事件 |

**结论：主因是后端根本没有生成；次要原因是前端只展示当前周。**
不能仅凭 UI 判断「一周后没有任务」，但这次后端确实也没有。

## 2. 根因（按因果链）

### 根因 R1（主因）：重复语义没有进入 deterministic 层

- `AnalyzedGoal` 没有 `goal_kind / recurrence`（`schemas.py:36`）。
- `plan_generation` 不接收 `goal_analysis`（`plan_generation.py:75-107`
  的 `PlanDrafterInput` 没有该字段）。
- 结果：「每天」只是自然语言 constraint，无法驱动展开。

### 根因 R2：展开触发条件过窄且会静默跳过

`_expand_recurring_goals`（`plan_drafter.py:142-213`）只在 LLM 路径调用，
并要求：

1. `task.goal_id` 必须是合法 1-based index（`plan_drafter.py:159, 174-181`）；
2. `_infer_task_kind(goal)` 必须不是 `ONE_OFF`（`plan_drafter.py:170-171`）；
3. group 里任何 draft 一旦有 `occurrence_date`，整组跳过（`plan_drafter.py:173`）。

任意一条不满足，就直接 `expanded.append(task)` 原样保留 —— **没有错误、没有
warning、没有 fail-closed**。这就是「LLM 返回 7 个第N天，系统照单全收」的直接原因。

### 根因 R3：`task_kind=long_term` 被错误等同于「每日重复」

`_infer_task_kind`（`plan_drafter.py:51-61`）：

```python
if goal.goal_type in {GoalType.LONG_TERM, GoalType.PROJECT}:
    return TaskKind.LONG_TERM   # -> 后续按天展开
```

`PROJECT`（课程/项目型）被错误地当作 recurring。这会制造「每天学习高等数学」
这类没有意义的重复。

### 根因 R4：LLM 被 prompt 诱导按天枚举

- `initial_plan.md:24`：「Split work into checkable units」。
- `goal_analysis.md:20-21`：要求 subtasks 具体可检查。
- 没有任何一句说「recurring goal 不要按日期枚举 occurrence」。
- 叠加 plan 默认 horizon 只有 13 天，模型自然输出「第1天…第7天」。

### 根因 R5：缺少 fail-closed 的重复校验

- `EarliestStartRule` 只保证 `scheduled_date >= occurrence_date`
  （`earliest_start.py`）。
- `DeadlineRule` 只保证 `scheduled_date <= deadline`（`deadline.py`）。
- 没有规则检查：
  - 同一 series 同一 occurrence_date 是否重复；
  - scheduled_date 是否等于 occurrence_date；
  - 声明的 recurrence 生命周期是否被完整物化；
  - occurrence_date 是否落在 goal 的 [start, end] 内。
- `_persist_final_plan` 还会**静默丢弃**没有排上槽位的 recurring occurrence
  （`plan_service.py:970-978`）——展开/容量出问题时，用户只会看到「少了一批任务」，
  不会看到失败。

### 根因 R6：scheduler 的 horizon/起点依赖 today，而不是 plan/goal 生命周期

- `default_horizon` 的 `start` 永远是 today（`scheduler.py:94`）。
- `end` 只被 task deadline 撑大；如果 draft 没有 deadline，就只有 13 天。
- plan 的 `end_date` 在 finalization 时直接复制 `request.end_date`
  （`finalization.py:44-45`），而 `request.end_date` 默认是 today+13
  （`plans.py:69-70`）。因此长期 goal 的 2027-07-01 不会进入 plan 元数据。

## 3. 为什么「第1～7天」全部在同一天？

按数据流还原：

1. LLM 输出 7 个 draft，title 分别是「第1天」…「第7天」。
2. 这 7 个 draft 没有 `occurrence_date`（LLM 被要求不输出日期）。
3. 展开条件未满足（R2），所以它们保持 `task_kind=ONE_OFF`、`occurrence_date=None`、
   `deadline=None`。
4. `drafts_to_tasks` 把它们变成 7 个普通 Task（`_shared.py:47-94`）。
5. `build_rule_context` 只给有 `occurrence_date` 的 draft 写
   `task_earliest_dates`（`_shared.py:181-182`），所以这 7 个任务都没有最早日期。
6. scheduler 从今天（10-26）开始贪心扫描；每天容量 300 分钟，7×20=140 分钟，
   全部塞进 10-26，时间从 10:15 开始按 20 分钟 + 15 分钟 buffer 排列。

**「第N天」是纯 UI 文本，不是日期约束；scheduler 从未读取它。**

## 4. 为什么只有一周？

- 后端常量是 13 天，不是 7 天（`constants.py:7`）。
- 7 是 LLM 自己枚举出来的条数（「第1天…第7天」）。
- 展开没有运行，所以没有 deterministic 的 249 天 occurrence。
- 前端「本周」只显示当前周（`selectors.ts:42-52`），进一步放大了「只有一周」的观感。
- 即使后端生成了更晚的任务，当前前端也没有月/更长周期的可见入口
  （月视图是占位，`index.tsx:594-601`）。

## 5. 哪些是 prompt 问题

1. `goal_analysis.md` 没有要求输出 `goal_kind / recurrence / work_units`，
   导致 LLM 的语义判断无法机器化。
2. `initial_plan.md` 的「Split work into checkable units」没有区分
   「一个 recurring template 内部的 checkable steps」和「按日期枚举 occurrence」。
   应明确：recurring goal 只输出一个可复用 template；不要输出 Day 1..Day N。
3. `initial_plan.md` / `replanning.md` / `adjustment.md` 都没有要求
   「保留 series_id / occurrence_date / 不把 series 拆成 one-off」。
4. 没有任何 prompt 禁止 LLM 计算日期跨度或枚举日期。

**但 prompt 不是根因本身。** 即使 prompt 写得再好，只要 schema 没有
`goal_kind/recurrence`，deterministic 层仍然拿不到语义；只要展开仍是条件性的，
模型输出仍可能绕过它。所以 prompt 修改必须排在 schema + deterministic 修复之后。

## 6. 哪些是 schema 问题

1. **Agent schema**：`AnalyzedGoal` 缺 `goal_kind / recurrence / work_units`
   （必须补）。
2. **TaskDraft**：已有 `task_kind/series_id/occurrence_date`，
   但缺 machine-readable 的 recurrence 元数据（frequency/interval/weekdays）
   供 deterministic 校验使用（建议补，不落库）。
3. **Goal schema**：DB/API 字段已够用；问题是默认值和 decompose 链路丢 `goal_type`
   （需小修，不需要新表）。
4. **不需要 recurrence template 表**：在「goal 行即 template」的方案下，
   `goals.task_kind / start_date / deadline / recurrence_weekdays /
   daily_target_minutes` 已经能表达 template。是否改成 rolling materialization
   是架构选择，不是本次 P0 的前置条件。

## 7. 哪些是 scheduler / API / frontend 问题

- **Scheduler**：
  - horizon 起点用 today 而不是 plan start；
  - 没有显式的 plan/goal horizon 输入；
  - 它本身没有「把 occurrence 拉回同一天」的错，错在输入没有 occurrence 约束。
  - 需要增加：显式 `schedule_start / schedule_end`，并让 occurrence 的
    `occurrence_date` + `deadline` 同时约束「必须落在当天」。
- **API**：
  - `GET /plans/{id}` 返回全部任务，没有 7 天过滤（这是对的，不需要改）。
  - 需要补的只是测试，证明「API 不会把 recurrence 生命周期截断到 7 天」。
- **Frontend**：
  - 只渲染今天 + 当前周；月视图占位。这是**展示层限制**，不是本次 P0 的
    数据正确性根因。按需求「UI 即使只显示未来 7 天，也不能意味着第 8 天以后不存在」，
    本次保证后端数据完整，前端长周期视图作为 remaining limitation 记录。

## 8. 最小修复方案（架构决策）

### 8.1 目标架构

```
Goal (start_date, deadline, task_kind, recurrence_weekdays, daily_target_minutes)
  + GoalAnalysisResult (goal_kind, recurrence, work_units)   <- LLM 语义
        |
        v
Deterministic resolver (explicit metadata > LLM classification > legacy goal_type)
        |
        +-- ONE_OFF  -> 1 个普通 draft
        +-- RECURRING -> RecurrenceRule -> deterministic occurrence expansion
        |                  -> series drafts (occurrence_date, series_id, index)
        +-- PROJECT  -> 有限 work_unit 序列（不按天复制）
        |
        v
Scheduler (occurrence_date = earliest, occurrence_date = deadline)
        |
        v
RuleEngine (series duplicate / wrong-day / completeness)
        |
        v
Persist (occurrence rows; 不再静默丢弃)
```

### 8.2 关键决策：eager full-range materialization（本次选择）

- 在 planning 时由 deterministic code 一次性生成 `start_date..end_date`
  的全部 occurrence（本次 249 条），写入数据库。
- 理由：
  - 与现有 `tasks.series_id/occurrence_date` 数据模型和测试完全兼容；
  - 不需要新增 recurring job / materializer / 后台任务基础设施；
  - 249 条 / goal 的规模对 SQLite/Postgres 都可接受；
  - scheduler 的 `occurrence_date==deadline` 约束能保证每天一条。
- 明确代价（写入报告）：
  - 每个 plan version 会复制整段 occurrence；replan 会新增 N 行；
  - 超长 goal（例如 10 年 daily = 3653 行）需要上限；
  - 本次设置 `MAX_OCCURRENCES_PER_SERIES = 2000`，超过则**明确失败**，
    不静默截断。
- 为什么不做 rolling：
  - 需要新增 template 持久化 + 读时 materialize + 幂等/去重 + 状态回填，
    改动面和回归风险显著高于本次 P0；
  - 用户明确允许「一次性物化完整范围更简单也可以保留，但必须说明影响」。
  - 本次把 expansion 收敛到单一 deterministic 模块，后续切换 rolling 时
    只需替换 materialization window，不影响 schema/规则。

### 8.3 责任边界

- **LLM**：只判断 `goal_kind`（one_off/recurring/project）、recurrence 频率、
  project 的有限 work units；不计算天数、不枚举日期、不输出 `第N天`。
- **Deterministic**：日期运算、边界（inclusive）、occurrence 展开、series id、
  order_index、scheduler 约束、容量、落库、校验。
- **禁止**：regex 解析「每天/每周」；根据 title「第N天」猜日期；
  复制最后一个 draft 填日期。

### 8.4 边界语义

- `start_date` 与 `end_date` 均 **inclusive**。
- DAILY：`start, start+interval, ... <= end`。
- WEEKLY：在 `start..end` 内，选择 `weekdays` 指定的星期；`interval` 以
  `start` 所在周为锚点，每 N 周一次。
- `weekdays` 为空 + weekly → 使用 `start_date.weekday()`。
- 同一天同一 series 恰好一个 occurrence。
- 空 occurrence / 非法范围 → `RecurrenceError`（fail closed）。

## 11. Regression test 设计

| # | 场景 | 断言 |
|---|---|---|
| 1 | 跨月 daily：2026-10-26 → 2026-11-05，每天背单词 | 11 个 occurrence；日期连续且唯一；不会全落到 10-26 |
| 2 | 长跨度：2026-10-26 → 2027-07-01 | 249 个 occurrence；首日=10-26，末日=07-01；无重复；plan end_date 覆盖 07-01 |
| 3 | one-off：10-30 前完成实验报告 | `goal_kind=ONE_OFF`；1 个 draft；无 series/occurrence |
| 4 | finite project：07-01 前学完高等数学 | `goal_kind=PROJECT`；有限 work units（不是 249 个 day copies）；`task_kind=ONE_OFF`；无 occurrence_date |
| 5 | weekly：每周六做英语模拟题 | 所有 occurrence 的 `weekday()==5`；首日是正确的周六 |
| 6 | capacity：daily recurring + 其他任务 | `daily_minutes <= daily_limit`；occurrence 不会被挪到别的日期 |
| 7 | boundary：start=end / end 前无匹配 weekday | inclusive 语义明确；非法/空 series fail closed |
| 8 | API/UI horizon：30 天 daily goal | `GET /plans/{id}` 返回 >7 天的任务；第 8 天以后存在；证明是 view horizon 而非生命周期截断 |

补充：

- 同一 series 同一 occurrence_date 重复 → rule violation。
- scheduled_date != occurrence_date → rule violation。
- 超过 `MAX_OCCURRENCES_PER_SERIES` → `RecurrenceError`。
- 现有 `tests/unit/test_task_kinds.py`、`tests/agent/test_preview_flow.py`
  继续通过（invalid range 按新契约改为 fail closed）。

## 12. 一句话总结

**事故不是「scheduler 只排了 7 天」，而是「LLM 的『每天』从未变成机器可读的
recurrence；deterministic expansion 因条件不满足被静默跳过；7 个无日期约束的
one-off 被 scheduler 贪心塞进同一天」。修复的核心是把 recurrence 语义显式化，
把日期展开收敛到一个 deterministic、可校验、fail-closed 的模块，而不是继续在
prompt 里堆文案。**
