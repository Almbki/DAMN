# 阶段 0：字段清单与迁移计划

> 依据：[实施指导.md](实施指导.md) 阶段 0。目标：以 `app/user_models/` 的**实际三层实现**为基线，列出我们额外需要的字段，并给出**兼容现有 V1.1 代码与真实 Postgres 数据**的迁移计划。
>
> 兼容原则：**不改现有列名、不删列、不改现有 API**。模型侧名字（`planned_start`、`estimated_duration_minutes`、`completion_ratio` 等）只出现在 `app/user_models` 边界适配器里，数据库和 API 继续用现有名字。

## 3. 实际三层实现 → 现有字段对照

### 3.1 `TaskPredictionContext`（Level 3 任务输入）

实际定义见 `app/user_models/contracts.py:123-134`：

| 模型字段 | 现有来源 | 处理 |
|---|---|---|
| `task_id` | `tasks.id` | 沿用 |
| `title` | `tasks.title` | 沿用 |
| `estimated_duration_minutes`（>0） | `tasks.estimated_duration` | 沿用；适配器透传 |
| `difficulty`（1–5，可空） | **无**；`user_model_service.task_context` 目前写死 `None` | **新增 `tasks.difficulty`（Integer，可空）** |
| `deadline`（datetime，可空） | **无任务级截止**；`_level2_task_plan` 和 `task_context` 目前写死 `None` | **新增 `tasks.deadline`（Date，可空）**；空时回退 `goals.deadline` |
| `planned_start`（datetime，可空） | `tasks.scheduled_date` + `tasks.start_time` | **不改列**；适配器组合；只有日期时用 `DEFAULT_DAY_START = 08:00`（`user_model_service.py:56`） |
| `task_type`（可空） | **无**；`task_context` 的 `task_type` 参数目前一直传 `None` | **新增 `tasks.task_type`（String(64)，可空）** |
| `available_time_minutes` | 排程容量 | 运行时传入，不落任务表 |

### 3.2 `TaskPlan` / `TaskExecution`（Level 2 每日输入）

实际定义见 `app/user_models/level2/ddsr/schemas.py:209-231`，映射见 `user_model_service.py:245-266`：

| 模型字段 | 现有来源 | 处理 |
|---|---|---|

| `TaskPlan.estimated_duration_minutes`（>0） | `tasks.estimated_duration` | 沿用；`max(..., 1)` |

| `TaskExecution.completion_ratio` | `task_executions.completion_rate` | 沿用 |
| `TaskExecution.completed` | `task_executions.completed` | 沿用 |
| `TaskExecution.interruption_count` | `task_executions.interruption_count` | 沿用；`NULL = 未观测` |

`DayInput` 的硬约束（`schemas.py:262-280`）：

- 同一天 `task_plans` 的 `task_id` 不能重复。
- `task_executions` 的 `task_id` 必须属于当天的 `task_plans`。
- `TaskPlan.planned_start` 必填；因此**没有 `scheduled_date` 的任务不会进入 Level 2**（`_build_days` 直接跳过）。

## 6. 迁移计划

基线：真实 Postgres `adde00b2004f`（已是 head），SQLite 开发库同样由 `create_all()`/Alembic 管理。全部为**新增**迁移，不改旧列；SQLite 用 `render_as_batch=True`，Postgres 正常 `ALTER TABLE`。

| # | revision 内容 | 回填 |
|---|---|---|
| 1 | `tasks` 加 `deadline`、`earliest_start_date`、`difficulty`、`task_type`、`value_score`、`completion_criterion` | 不回填；空值走回退 |
| 2 | `task_dependencies` 表 | 无 |
| 3 | `task_events` 表 | 无 |
| 4 | `task_executions` 加 `execution_status`、`failure_category`、`estimate_feedback` | `execution_status` 按 `completed` + `completion_rate` 回填 |
| 5 | `feedbacks` 加四段反思 + `day_closed_at` | 不复制 `free_text` |
| 6 | `evidence_items` 表 | 无 |
| 7 | `daily_states` 表 | 可用 `user_states.level2_profile` 回填最新一天（可选） |
| 8 | `prediction_snapshots` + `prediction_outcomes` 表 | 无 |

顺序：1 → 2/3 → 4 → 5 → 6 → 7 → 8。每步独立可回滚；`downgrade()` 只删除本步新增的表/列。

兼容措施：

- 现有 `Task` / `TaskExecution` / `Feedback` 的必填字段不变；新字段全部可空。
- API `TaskRead` / `TaskUpdateRequest` / `FeedbackCreate` / `FeedbackRead` 只加可选字段，不删不改现有字段。
- `task_standards`、`is_flexible`、`target_unit`、`completion_rate`、`actual_duration` 等继续使用；模型侧在 `app/user_models` 适配器转换。
- 旧 `shadow_predictions`、`prediction_logs` 保留；新预测写新表，shadow 仍只写审计。
- 不在本阶段删除任何旧表/旧列；清理放到阶段 5 之后。
- Postgres 有真实数据（17 用户 / 65 任务 / 16 执行 / 3 反馈），迁移必须先备份，再在副本上演练。

## 7. 待确认口径（已于 2026-10-25 确认）

1. `planned_start` 只有日期没有时间时，继续用 **08:00**（`DEFAULT_DAY_START`）。
2. “价值”单独建 `tasks.value_score`（1–5，可空），不复用 `priority`。
3. “拆分单位”复用现有 `target_amount` / `target_unit`，不新增 `split_unit`。
4. `task_standards`（子步骤清单）保留；另新增 `tasks.completion_criterion` 文本，两者互补。
5. 新增 `tasks.earliest_start_date`（可空）；为空时回退 `occurrence_date`。
6. `daily_states` 按日保留，只保留最近 **180 天**，更早的自动删除。

隐私与安全最小落地：阶段 1 不做，阶段 5 再统一安排（见 `docs/决策记录.md` §9）。
