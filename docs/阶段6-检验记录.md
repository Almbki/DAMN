# 阶段 6：检验与试点（2026-10-25）

> 依据 [实施指导.md](实施指导.md) 阶段 6。这一页只记录**机制检验**，不是效果研究：
> 使用者是 5 个合成场景（不是真人），模拟 7 天，没有真实长期结果数据。
> 因此**不声称预测准确**，也不做统计显著性结论。

## 1. 方法

- 脚本：[scripts/simulate_usage.py](../scripts/simulate_usage.py)。
- 每个合成场景 = 一个「模拟使用者」：注册 → 导入该场景的既有观察（Level 1/2/任务/反馈）→ 用真实 HTTP API 生成一份计划（阶段 4 调度器）→ 连续模拟 7 天：
  - 当天任务按人设概率被标记为完成 / 部分完成 / 没做（带实际用时）；
  - 每天提交晚间反馈（完成率、压力、精力、四段反思文本、预估准确性、是否结束今天）；
  - 后端按阶段 5 的策略选择 顺延 / 小修 / 大改，脚本继续使用最新计划。
- 指标：完成率、日均任务数、计划版本数、顺延/小修/大改次数、实际/计划用量、最长等待天数。
- 输出：本页表格；脚本同时写 `.tmp/simulation/report.json` 与 `report.md`。

## 3. 观察

1. **顺延生效**：低完成、无压力的三个使用者各触发 4–6 次顺延，计划版本保持 2 版——任务内容没有被重排，只是被挪到明天，符合「顺延不新建版本」的设计。
2. **大改冷却生效**：超载型第一晚触发 1 次大改后，后续同一天内的大改请求被冷却拦下并降级为顺延；一周内大改次数为 1，符合「一周最多一次大改」的目标。稳定/恢复/截止/拖延型大改 0 次。
3. **小修频率偏高（观察项，不是硬指标）**：截止压力型因每天压力高触发 7 次小修、产生 9 个计划版本。设计只对「大改」设冷却，小修目前可以每天发生。是否给小修也加最低间隔，列入后续待定项（需要真实记录判断它是否真的打扰用户）。
4. **完成率随人设变化**：30%–100%，说明机制对行为差异有响应；但这是合成人设的设定值，不能当作「系统提升了完成率」的证据。
5. **最长等待 0–6 天**：拖延型等待最长（6 天），稳定/超载型最短；数值受 7 天窗口和阶段 4 的突发预留（默认 60 分钟）影响，日均任务只有 0.29–1.43 个，偏低。
6. **实际/计划用量 1.0–1.4**：与每个合成人设设定的用时倍率（1.0–1.4）一致，说明自动实际用时与估时统计链路一致。

## 4. 结论与回退判断

- 机制按设计工作：顺延、反馈三档、大改冷却、每日反馈、估时/实际统计都产生了预期结果；**不需要回退**阶段 4 的调度器或阶段 5 的反馈策略。
- 不能声称：预测准确率、真实完成率提升、用户满意度。这些需要真实记录的前后比较。
- 已知观察项（留到有真实数据再定）：小修频率、日均任务密度、7 天窗口太短。

## 5. 如何复跑

```powershell
# Windows 下不要用 uv run（uv 缓存被沙箱挡住），直接用 venv Python
.\\.venv\\Scripts\\python.exe scripts\\simulate_usage.py
```

结果会打印到 stdout，并写到 `.tmp/simulation/`（不提交）。
