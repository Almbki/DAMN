# 痛点分析与需求建议（Product Pain Points & Requirements）

> 基于对当前代码的完整审查。目标：指出**当前功能哪里不可信/不好用**，并给出**切中痛点、可落地**的新需求。
> 相关：`docs/replan-trigger-design.md`（重排与 backlog 的深入设计）。

---

## 1. 当前功能的整体评价

**做得好的**：
- 分层纪律强（domain/core 零框架依赖、仓储不 commit、RuleEngine 单一权威）。
- 闭环设计完整（goal → plan → execute → feedback → profile → replan），版本不可变 + `ReplanEvent` 审计。
- 画像有冷启动先验 + EWMA 自适应，且**诚实标注** `degraded`。
- 硬约束具象且可测（7 条规则 + 确定性排期）。

**核心问题一句话**：**闭环形式完整，但闭环里的“信号”大多是用户自评 + mock 预测，既不可信、也难以衡量**，导致“自适应”目前更像“按固定规则换个版本”。

---

## 2. 核心痛点

### P1. 信息不可信（最致命）
- `app/ml/**` 全是 `statistical-*` 统计 mock，**没有任何训练模型**；画像公式系数全是【工程】估计。
- 预测（时长/完成率/压力）**没有把置信度/来源暴露给用户**；`prediction_logs` 只写不闭环。
- 后果：计划里的“预计 90 分钟”“完成概率 0.7”用户无法判断可信度；产品对外宣称“自适应”有夸大风险。

### P2. 拆解难以衡量
- `TaskStandard`（可量化“完成标准”）存在，但**没有强制、没有校验**；任务完成是**布尔**，`Feedback.completion_rate` 是**整体自评 0~1**。
- 拆解粒度靠启发式（按换行/分号切），**无法衡量拆得好不好**。
- 后果：无法验证一个任务是否真的“做完”；反馈数据本身不可信 → 训练数据不可信。

### P3. 反馈负担重、数据稀疏
- 每日 `Feedback` + 每任务 `TaskExecution` 都靠手动填写；样本增长慢，冷启动久（画像 `degraded = update_count < 3`）。
- 后果：模型永远“喂不饱”，自适应长期停在先验阶段。

### P4. 计划不可解释、不可控
- 用户不知道为什么这样排、为什么被拆成这些子任务、为什么某任务被丢弃（`plan_repair` 会丢低优先级任务）。
- 用户无法 **pin/锁定** 某个任务或时间段，无法表达“今天别排数学”。

### P5. 重排抖动、信任受损（详见重排文档）
- 当前反馈路径**无冷却/预算**；**任意自由文本必触发全量重排**；`changed_task_ids` 失真。
- 后果：计划频繁变，用户觉得“它老在动我的日程”。

### P6. 缺少“未完成/逾期”闭环（backlog）
- 任务没做完，除了更新画像外**没有处理**：不 roll-forward、不 decay、不 re-break、不 drop。
- 后果：未完成任务在版本间静默积累或丢失，没有“人类可理解”的交代。

### P7. 已排期时新增任务语义不清（详见重排文档）
- 前端已有 `task-add-dialog`，但后端没有明确的“插入/局部修复/全量重排”策略与 case 分类。

### P8. 单一信号（完成率）过于粗暴
- 完成率阈值 0.5、画像 0.4×5天/0.6×2天 是拍脑袋阈值，未基于数据校准，易误触发。

---

## 3. 建议新增的需求（按优先级）

> 每条给出：**针对痛点 → 方案 → 落地改动点 → 难度**。

### R1（P0）证据化完成度：让“done”可衡量
- **方案**：以 `TaskStandard` 勾选比例作为任务完成度（evidence-based completion）；任务完成 = 勾选率达到阈值；引入可选“产出物/证据”字段（链接/文本/时长）。
- **改动**：`TaskStandard.completed` 聚合成 `task.completion_ratio`；`PATCH task` 支持逐条勾选；`Feedback.completion_rate` 可自动汇总（减少手动）。
- **难度**：中。**收益**：直接解决 P2，并提升训练数据质量。

### R2（P0）预测可信度暴露
- **方案**：每个预测输出 `{value, source, confidence/degraded}`；UI 诚实标注“先验估计/样本不足”；`prediction_logs` + `scripts/evaluate_predictors.py` 建立离线评估门槛。
- **改动**：`app/ml/base.py` 预测结果加 `confidence`/`sample_size`；mappers 暴露；前端展示。
- **难度**：低-中。**收益**：解决 P1 的“不可信”。

### R3（P0）重排仲裁统一（见 `replan-trigger-design.md`）
- **方案**：单一仲裁器 + 冷却/滞后/日预算/最小改进门槛；自由文本不再无条件全量重排；修正 `trigger_type` 与 `changed_task_ids`。
- **改动**：新增 `domain/replan/policy.py` + `application/services/trigger_service.py` + 新表 `replan_trigger_evaluations`。
- **难度**：中。

### R4（P1）未完成 backlog 处理（见 `replan-trigger-design.md` §6）
- **方案**：capacity-aware roll-forward + 决策树（habit 只滚下一次 / 硬 DDL 升级+re-break / 反复推迟→decay/drop）；设 rollover 上限，超限强制 triage。
- **难度**：中。

### R5（P1）新增任务插入阶梯（见 `replan-trigger-design.md` §5）
- **方案**：最便宜优先——先找空隙直插，再局部修复，最后才全量重排；把“稳定性”作为目标项。
- **难度**：中。

### R6（P1）降低反馈负担 + 被动采集
- **方案**：微反馈（单点 emoji / 一键）；从 `TaskExecution` 的时间戳/勾选行为自动推断，减少必填。
- **难度**：低-中。**收益**：解决 P3，加速冷启动。

### R7（P2）可解释性与用户可控
- **方案**：每个任务给“为什么这样排”（基于理论工作量 + 画像 + 命中的规则）；支持 `pin`/锁定、`avoid`（今天不排 X）。
- **难度**：中。

### R8（P2）任务粒度与拆解质量度量
- **方案**：记录拆解来源与粒度分布；用“子任务数/预估时长/可执行性”评估；A/B 不同粒度对完成率的影响。
- **难度**：中-高（偏研究）。

### R9（P2）RAG 只用于“生成/修复”，不用于触发
- **方案**：检索用户历史计划、`TaskStandard` 模板、相似情境 → 作为 plan_drafter / repair 的 few-shot 依据（提升拆解与修复质量）。
- **改动**：优先复用现有 `memory_retriever` + `agent_memories`，不必先上向量库；先做“结构化检索 + 过滤”。
- **难度**：中。**注意**：绝不用于“是否重排”的判定。

### R10（P3）周期仪式：每日收尾 + 每周 triage
- **方案**：每日 shutdown 确认明天计划；每周强制清理 backlog（keep/split/drop）。
- **难度**：低。

## 4. 需求优先级总表

| 编号 | 需求 | 针对痛点 | 优先级 | 难度 |
| --- | --- | --- | --- | --- |
| R1 | 证据化完成度（TaskStandard 驱动） | P2 | P0 | 中 |
| R2 | 预测可信度暴露 + 离线评估门槛 | P1 | P0 | 低-中 |
| R3 | 重排仲裁统一 + 冷却/预算 | P5, P8 | P0 | 中 |
| R4 | backlog 处理 | P6 | P1 | 中 |
| R5 | 新增任务插入阶梯 | P7 | P1 | 中 |
| R6 | 微反馈 + 被动采集 | P3 | P1 | 低-中 |
| R7 | 可解释性 + pin/avoid | P4 | P2 | 中 |
| R8 | 拆解质量度量 | P2 | P2 | 中-高 |
| R9 | RAG 用于生成/修复 | P1, P2 | P2 | 中 |
| R10 | 每日收尾 + 每周 triage | P3, P6 | P3 | 低 |

---

## 5. 一句话结论

当前系统“**结构上已经是自适应系统，数据上还不是**”。最该投入的不是更多 Agent，而是：
1. **让完成度可信**（R1）、
2. **让预测可信/透明**（R2）、
3. **让重排有纪律**（R3）。

这三点做完，系统才真正“自适应”；RAG/微调模型都应排在它们之后。
