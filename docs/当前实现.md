# 当前实现（远端 V1.1-test）

> 这页写的是**代码现在实际怎么工作**，不是目标设计。目标设计见 [架构.md](架构.md)、[决策记录.md](决策记录.md)、[三层用户模型.md](三层用户模型.md)；从现状到目标的差距见 [实施指导.md](实施指导.md)。
>
> 基线：`V1.1-test`（2026-10-24）+ 阶段 1–6（2026-10-25，含合并远端新版本）。测试策略为增量：保留既有测试并新增阶段测试，默认只跑受影响文件。当前迁移 head：`49623649564a`。

## 1. 模块关系

```
API（app/api, app/schemas）
  → Application（app/application）
      → Agent 旁路（app/agent）
      → User Models 旁路（app/user_models）
      → Domain（app/domain）
      → Infrastructure（app/infrastructure/database, llm）
```

- `app/agent`：LangGraph 编排、节点、工具；不碰数据库，数据由 `PlanService` 通过上下文注入。
- `app/user_models`：Level 1/2/3 模型运行时；不碰数据库、FastAPI、调度器；真实模型代码和 artifacts 在这里。
- `app/ml`：**已删除**；旧的统计 mock 和 `ml_prediction` 节点不存在。
- `app/domain`：实体、规则引擎、调度器、反馈策略；不 import FastAPI/SQLAlchemy/LangGraph。
- `app/infrastructure`：SQLAlchemy 模型、仓储、LLM 客户端。
- `new_frontend/`：当前前端；旧的 `frontend/` 已不在远端基线。

三条边界仍然成立：规则引擎是硬约束唯一权威；调度器不调用大模型；仓储只 `flush()`，事务由服务负责。

## 2. 数据来自哪里

| 数据 | 谁产生 | 什么时候产生 | 谁消费 | 存在哪 |
|---|---|---|---|---|
| 目标 | 用户创建目标 | `POST /goals` | 计划生成 | `goals` |
| 计划 / 任务 / 任务标准 | 计划生成 + 用户确认 | 生成、确认、重排 | 排程、执行、反馈 | `plans`、`tasks`、`task_standards` |
| 任务执行 | 用户 PATCH 任务 | 完成，或提交任一执行字段 / `completion_rate` | Level 2、预测评估、洞察 | `task_executions` |
| 每日反馈 | 用户提交每日反馈 | `POST /plans/{plan_id}/feedback` | 重排策略、Level 2 | `feedbacks` |
| 任务变更事件 | 用户 PATCH/DELETE 任务 | 每次任务更新/删除（只追加） | 审计、修正回放 | `task_events` |
| 任务依赖 | 草案确认时 | 生成/重排落库 | 后续排程消费（目前只存不用） | `task_dependencies` |
| 反思证据 | Level 2 证据抽取 | 反馈刷新时（LLM，失败回退规则） | Level 2 状态、审计 | `evidence_items` |
| 每日计划审计 | 调度器 + 计划落库 | 生成/重排时 | 容量解释、装不下理由回放 | `daily_plans`、`unscheduled_tasks` |
| 每日状态历史 | Level 2 刷新 | 反馈/执行之后，每次 replay 全量重写 | 回放、阶段 6 评估 | `daily_states`（只留最近 180 天，`data_origin` 按当天数据） |
| 预测快照 | Level 3 shadow | 计划 commit 后、推理前 | 诚实评估预测 | `prediction_snapshots` |
| 预测结果 | 任务执行记录后 | 用户完成/部分/没做时 | 预测评分 | `prediction_outcomes` |
| Level 1 稳定特质 | CAT 测评 | 首次测评 / 重测 | Level 2、Level 3 shadow | `users.trait_profile`、`trait_assessments` |
| Level 2 每日状态 | 模型服务 | 反馈或执行之后，best-effort 刷新 | Agent、画像页 | `user_states.level2_profile` + 投影列 |
| Level 3 预测 | shadow runner | 计划 commit 之后 | 只写审计，不控制生产 | `shadow_predictions` |
| 重排事件 | 重排服务 | 反馈触发 / 手动重排 | 冷却、版本链 | `replan_events` |
| 日程占用 | 用户导入课表 | `POST /schedules/import`（CSV/XLSX） | 调度容量、规则 | `schedule_events` / `fixed_events` |

**TaskExecution 的写入条件**（`app/application/services/plan_service.py:615-677`）：`completed=true`，或请求里带任一执行字段，或带 `completion_rate`，就追加一条执行记录；重复 PATCH 会追加多行，不是覆盖。部分完成也会记录。

**每日反馈（阶段 5）**：`feedbacks` 有四段反思列和 `day_closed_at`。前端反馈页只放**一个引导文本框**写四段，保存到 `day_review`（旧 `free_text` 仍兼容）；Level 2 适配器把四段一起传给 `ReflectionInput`。反馈策略三档：无压力且完成率 < 0.5 → **顺延**（只挪未完成任务到明天，不新建版本）；有压力 → 小修；持续差/严重 → 大改（大改有冷却，冷却中降级为顺延）。`close_day` 置 `day_closed_at`，应用内当天不再提醒。

**证据抽取（阶段 2）**：Level 2 用 LLM 抽取证据（配置真实 `LLM_PROVIDER` 时；失败按天回退规则），accepted 证据写入 `evidence_items`；抽取失败不编证据、不阻断反馈。

**晚间提醒与估时统计（阶段 5）**：提醒默认开启、每天 22:00（应用内 gate + 系统通知，当天已写反馈应用内不再弹）。点过「开始」的任务完成时后端按起止时间自动算实际用时；只对「直接完成且从未开始、也没有实际分钟」的任务在晚间反馈问三档估时准确性；反馈结果显示当天估时 vs 实际，画像页显示近 7 天（`GET /users/me/estimate-accuracy`）。

## 3. 怎么存储

- 24 个 ORM 模型（不含 `__init__`）：15 个旧表 + `generation_jobs`（远端新版本）+ 阶段 1 的 `task_dependencies`、`task_events`、`evidence_items`、`daily_states`、`prediction_snapshots`、`prediction_outcomes` + 阶段 4 的 `daily_plans`、`unscheduled_tasks`。`users.mbti_type/mbti_dims` 已被远端 `remove_legacy_mbti_20261025` 删除（MBTI 不再是持久化概念）。关键表：`users`、`goals`、`plans`、`tasks`、`task_standards`、`task_executions`、`feedbacks`、`replan_events`、`user_states`、`trait_assessments`、`shadow_predictions`、`schedule_events`、`fixed_events`。
- 当前 head：`49623649564a`（共 23 个迁移）。`docs/database/数据库迁移.md` 的旧 head 行可能过时，以 `uv run alembic heads` 为准。
- SQLite 开发库由 `lifespan` 的 `create_all()` 建；Postgres 走 Alembic。
- JSON 列是允许的，但只用于审计/快照：`users.trait_profile`、`users.scheduling_preferences`、`user_states.level2_profile`、`shadow_predictions.input_summary/shadow_prediction`、`feedbacks.task_reasons`、`replan_events.changed_tasks`、`task_events.before/after`、`daily_states.profile_json`、`prediction_snapshots.trait/state/task/context/history/feature_snapshot`、`daily_plans.tasks/reasons`。不是把整个模型历史存 JSON 文件。
- 固定负载只能通过 CSV/XLSX 导入 `schedule_events`；没有手工 busy-block 接口。导入支持 `dry_run`、`term_start`，最大 2 MB / 1000 行。

## 4. 当前调度实际怎么排（阶段 4 后）

**容量**（`app/domain/scheduling/scheduler.py`）：每天容量 = `min(daily_limit_minutes, available_minutes_per_day) − 当天 fixed_events 分钟`；工作窗口 8:00–22:00、槽位 15 分钟、高认知上限与主题冲突等硬约束仍然由 `RuleEngine` 最终裁决。

**装箱顺序**：

1. 钉死任务（`is_flexible=False`）；
2. 为突发预留 `scheduler_burst_reserve_minutes`（默认 60 分钟）；
3. 长期任务（`task_kind=LONG_TERM`）的每日最低额度 `scheduler_long_term_daily_floor_minutes`（默认 30）；等待超过 `scheduler_long_term_max_wait_days`（默认 7 天）的长期任务提前；
4. 截止任务：截止日在 `scheduler_deadline_acceleration_days`（默认 3 天）内的进入加速组；
5. 当天杂事（低认知/恢复类）；
6. 其他任务。

**产出与持久化**：`CandidateSchedule` 现在带 `daily_plans`（每天容量/用量/任务/理由）和 `unscheduled_reasons` / `unscheduled_tasks`（capacity/deadline/long_term_wait/no_slot）；计划落库时写入 `daily_plans` / `unscheduled_tasks`，`PlanService._persist_task_dependencies` 把草案 `depends_on` 写入 `task_dependencies`。**调度器仍然不调用大模型。**

顺延/rollover：反馈策略的 `postpone` 路由只把当天未完成任务 `scheduled_date` 挪到明天（不新建版本）；明天容量不足时回落小修。

**还没做的**：

- 「第二档偏差只重排未来三天」：`micro_adjust` 仍重投整个 horizon；
- 截止任务装不下时的三选一交互（延期/缩范围/加时间）；
- 「当天覆盖默认容量」的按天接口（目前只有 per-plan 请求覆盖）；
- 依赖关系目前只做格式检查与落库，调度/规则还不消费 `task_dependencies`；
- 突发预留/长期额度/截止加速这些数值是工程默认，等真实记录再调（决策记录 §11）。

**目标设计与现状的差异**见 [实施指导.md](实施指导.md) 的「阶段 4」；不要在没改代码前按 [架构.md](架构.md) §4 理解当前行为。

## 5. 三层模型现在怎么跑

- Level 1：真实 CAT/GRM 运行时，输出五维 `theta/se/ci95/items_answered`；存在 `users.trait_profile` + `trait_assessments`。
- Level 2：真实 DDSR-V1 运行时；反馈/执行后刷新 `user_states`（最新单行）并**按日写 `daily_states`**（只留 180 天）；输入已含四段反思、任务级 deadline/difficulty（`task_type` 只进 Level 3，不进 Level 2）。证据抽取接 LLM（配置真实 provider 时）+ 规则兜底，写 `evidence_items`；状态差的失败记录从长期用时比例历史里剔除。
- Level 3：**shadow only**。计划 commit 后由 `Level3ShadowRunner` 运行，写 `shadow_predictions`；阶段 1 起推理前先把输入冻结进 `prediction_snapshots`，任务执行后写 `prediction_outcomes`；生产排程不读它。`LEVEL3_MODE=active` 也会被降级为 shadow。
- 生产用时估计：确定性的 `TaskEstimatorTool`，不是 Level 3；排程用 `predicted_duration or estimated_duration`；完成概率为空时按 1.0 处理。
- 反馈与提醒（阶段 5）：晚间提醒默认 22:00 开启，应用内到点弹窗（可稍后 2 次），当天已写反馈不再弹；反馈页一个引导文本框写四段；顺延/小修/大改三档，大改有冷却（冷却中降级顺延）；`close_day` 记录当天结束。
- `models_test/` 是冻结的测试/参考包，不是运行时；真实现在 `app/user_models/`。

## 6. 测试与证据现状

- 后端 229 个既有测试 + 各阶段新增增量测试（阶段 1 的 `test_phase1_*` 等 24 条；阶段 2 `test_phase2_evidence_extraction` 7 条；阶段 3 `test_decompose_validation` 20 条；阶段 4 `test_scheduler_phase4` 17 条 + `test_phase4_schedule_persistence` 2 条；阶段 5 `test_phase5_feedback` 10 条 + 策略用例；阶段 6 是脚本不是测试）。测试文件共 45 个，主要是契约/回归/架构测试，不是效果实验。
- Level 1 有官方数据仿真验证：`app/user_models/level1/artifacts/cat_validation.json`（619,150 人；MAE 0.198；10.33 题/维）。
- Level 2：54 个测试、13 项检查；没有大规模长期预测有效性。
- Level 3：冷启动/历史基线有实现；学习模型未训练；没有真实长期结果数据。
- 当前调度常量（300/480/15 分钟/2 个高认知/8:00–22:00/13 天、阶段 4 的 60/30/3/7 等）都是工程默认，不是研究结论。
- 阶段 6 做了合成人设的机制检验（见 [阶段6-检验记录.md](阶段6-检验记录.md)）：顺延、大改冷却、估时统计按设计工作；没有真实长期数据，不声称预测准确。
- 没有有效性实验；`scripts/evaluate_predictors.py` 只有脚本，没有数据/结果文档。
