# 「知衡 · AI 自适应任务规划系统」答辩文档

> 参赛赛道：AI + 软件创新（算法创新）
> 一句话定位：**一个会"反省"自己的计划系统** —— 不是让你学得更久，而是让你在截止前完成该做的事，然后放心地玩。

---

## 一、背景

计划类工具长期停留在"静态清单"：写完就扔，执行不下去只会怪自己。

| 目标人群 | 真实痛点 |
| --- | --- |
| 完美主义 / 焦虑者 | "总觉得学得不够"，无法安心休息 |
| 拖延人群 | 计划赶不上变化，越拖越焦虑 |
| 考研 / 考公 / 考证 | 多科目并行，时间与认知负载难以权衡 |
| 学生群体 | 假期/学期目标管理，缺少执行反馈 |

三个共性缺口：**① 计划不会根据执行情况调整；② 不区分任务的认知消耗；③ 只关心"学多久"，不关心"是否安心"。**

本项目从真实的个人需求出发（作者本人即目标用户，已有 v1→v4 的真实迭代反馈），把上述痛点工程化为一套可运行软件。

---

## 二、项目介绍

**核心机制：规划 → 执行 → 反馈 → 重排 的闭环**，与架构图完全一致：

```
开始 → 用户创建周期计划 → 任务是否清晰
        ├─ 否 → 智能体生成提问，使任务可得到合理拆分 ─┐
        └─ 是 ────────────────────────────────────────┴→ 生成 V1 版任务清单
                                              ↓
                                    用户尝试执行 ──────────────┐
                                              ↓                │
                                   记录用户状态反馈            │（主动申请生成新版本）
                                              ↓                ↓
                     冷启动 → 群体统计/用户画像模板 → 更新特征库/ML 状态 → 重排策略路由
                                              ↓                          │（轻微偏离/严重偏离）
                                        用户画像记忆 → 构建提示词 → Agent ⇄ Tools Call
                                                      ↓
                                            生成新版本任务计划 → 回到"用户尝试执行"
```

- **输入**：一份目标清单（如暑假计划）。
- **输出**：每日/每周可执行任务 + 反馈驱动的版本化重排（v1 → v2 → …）。
- **两种路径**：① 主动申请新版本（走冷却周期判定）；② 执行偏离后由系统自动路由重排。

---

## 三、项目创新点（产品层）

1. **反馈驱动的动态迭代（核心创新）**：把 RLHF 的"人类反馈校正"思想搬到任务规划——用真实执行反馈（完成率/压力/精力/原因）持续校正计划，而不是一次性生成。系统中体现为 **v1→v2→v3→v4** 的真实演进。
2. **认知负荷调度模型**：任务分级（高/中/低认知），高认知排在清醒时段、同类高认知不扎堆、任务间插入恢复项与缓冲——**认知科学 × 任务调度的工程化融合**。
3. **反焦虑设计哲学**：完成即休息、限时+缓冲、超时即停，目标从"提高时长"改为"减少失控感"。
4. **完成标准可量化拆解**：把"复习数学"拆成可勾选子标准（看课/例题/习题/总结），消除"什么叫学完了"的歧义。
5. **冷启动画像**：新用户无历史数据时，用**群体统计的 MBTI 画像模板**给出先验，再用在线反馈逐步覆盖——解决个性化系统的"第一天就冷冰冰"问题。

## 四、技术栈

| 层 | 技术 |
| --- | --- |
| 前端 | React Native + **Expo SDK 57**（expo-router、TypeScript）；`expo/fetch` 真流式 |
| 后端 | Python 3.12 · FastAPI · Pydantic v2 |
| 编排 | **LangGraph** 多节点状态机（两张图：初次规划 / 反馈闭环） |
| LLM | OpenAI 兼容接口（DeepSeek），`json_object` 结构化输出 + 客户端校验/重试/降级 |
| 数据 | SQLAlchemy 2 · Alembic · PostgreSQL（开发可 SQLite）；psycopg3 + 连接池 |
| 实时 | 异步 Job + **SSE** 逐节点进度 + 轮询兜底 |
| 质量 | pytest 全量回归（含端到端闭环）+ ruff + 前端 tsc |

## 五、技术实现（严格对应架构图节点）

| 架构图节点 | 系统实现 |
| --- | --- |
| 用户创建周期计划 | `POST /plans/preview` 提交目标；**异步 Job 立即返回 202**，后台线程独立 DB 会话执行 |
| 任务是否清晰 / 智能体提问 | `goal_analysis` + `classify_request` 节点；不清晰时走 `preview/adjust` 的对话式澄清 |
| 生成 V1 版任务清单 | **图 A**：`goal_analysis → theoretical_analysis → user_situation_analysis → plan_generation → rule_validation →（必要时 plan_repair）→ preview` |
| 冷启动 / 群体统计画像模板 | MBTI 先验模板 + `user_states` EWMA 状态（`duration_factor`/完成能力/压力） |
| 用户尝试执行 | 任务落库为**不可变计划版本**，前端按日/周展示并勾选 |
| 记录用户状态反馈 | `POST /plans/{id}/feedback`：完成率、压力、精力、原因分类 |
| 更新特征库 / ML 状态 | 统计预测器（耗时/完成率/压力/时段）+ EWMA 在线校准；`prediction_logs` 记录每次预测 |
| 用户画像记忆 | `agent_memories` + `user_states`，作为后续提示词的上下文 |
| 重排策略路由 | `adjustment_router`：**NO_CHANGE / MICRO_ADJUST（轻微偏离）/ FULL_REPLAN（严重偏离）** |
| 主动申请新版本 | `POST /plans/{id}/replan` |
| 冷却周期？ | **按用户**的重排冷却（默认 24h），未到点返回 409 + `next_eligible_at` |
| 构建提示词 → Agent ⇄ Tools | Prompt 模板（带版本号）+ 记忆检索；**图 B** 驱动 Agent，工具集：任务拆解、负载估算、计划起草、排程、规则校验、耗时预测、记忆检索、用户统计 |
| 生成新版本任务计划 | `v(n+1)`，旧版标记 `superseded`，写 `parent_plan_id` 与 `ReplanEvent`，回到"用户尝试执行" |
| （支撑）实时进度 | `GET /plans/generation/{job_id}/events` 实时 SSE 逐节点推送；`GET /plans/generation/{job_id}` 轮询兜底 |

**分层约束**（架构不腐化的关键）：`API → Application → Domain/Core → Infrastructure`；`agent`/`ml` 为侧挂。Agents 不碰数据库、**Scheduler 绝不调用 LLM**、仓储只 `flush` 不 `commit`、API 不返回 ORM 对象。

## 六、技术创新点（工程层）

1. **"LLM 只产候选，规则引擎是硬约束的唯一权威"**：DDL 截止、每日上限、缓冲、高认知上限、同日冲突等由 `RuleEngine` 确定性校验，LLM 输出永远不能直接决定约束是否满足；违规进入**有界修复循环** `plan_repair`。这让系统既有生成灵活性，又有可验证的正确性。
2. **计划版本不可变 + 每次重排可追溯**：`v(n+1)` + `superseded` + `parent_plan_id` + `ReplanEvent`，配合按用户冷却，形成可回放、可审计的自适应闭环。
3. **预测可评估（ML 可持续迭代）**：`prediction_logs` 对每次预测记录模型版本、特征指纹（`feature_hash`）与**真实来源**，可与 `task_executions` 的真实结果 join，计算 MAE / Brier——解决"AI 预测无法量化好坏"的问题。
4. **真·流式生成体验**：把"同步跑完再回放"的伪 SSE 重写为**真异步 Job + 实时 SSE**（后台线程 + 独立会话 + 条件变量推送 + 心跳），并保留**轮询兜底**；前端用 `expo/fetch` 原生流式消费。生成过程逐节点可见，长任务不再触发前端超时。
5. **LLM 接入的工程稳健性**：统一 OpenAI 兼容客户端，默认 `json_object` 而非 `json_schema`（规避 DeepSeek 400）、失败自动降级为确定性启发式、进程级单例复用连接池——**"AI 不可用时系统仍可交付"**。
6. **契约优先的前后端协作**：OpenAPI 对齐 + `mapper` 隔离层 + 统一错误信封 `{code, message, detail}` + 16 个前端契约测试，保证接口演进不破坏客户端。

## 七、验证与成效

- **端到端闭环测试**：`generate → execute → 低完成率反馈 → 自动重排 v2 → 冷却 409`。
- **全量回归**：后端 pytest 全绿（含异步 Job、SSE 流式、契约测试）；前端 `tsc` 通过。
- **实时性实测**：拆解请求 **0.04s 返回**并开始逐节点推送（`goal_analysis → … → plan_generation → rule_validation → completed`），全程约 25s 可视化，不再出现"前端超时、后端仍在跑"。

---

## 八、总结与展望

本项目的核心不是"再做一个待办清单"，而是把 **反馈驱动的自适应闭环**、**认知负荷调度**与**硬约束规则引擎**工程化为一套可运行、可验证、可迭代的软件系统；同时用真实使用反馈（v1→v4）证明其有效性。

**下一步**：接入真实训练模型替换统计预测器（`prediction_logs` 已备好数据资产）；扩展目标分层（年/月/周/日）；增加日历与提醒集成、数据洞察面板。
