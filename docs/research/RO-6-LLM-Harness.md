## 4. 方案设计

### 4.1 LLM 门控三层（L0–L2 + 弃答）

> **通俗说明**：不是每一步都叫大模型。先让"不费脑的"处理，只有难题才升级。

| 层 | 触发 | 干什么 | 例子 | 依据 |
|---|---|---|---|---|
| **L0 确定性** | 规则/模板/求解器可覆盖 | RuleEngine、Scheduler、模板拼装、KLM 估时 | 按依赖图排序、算间隔 | 方向10 [1][2][3]；方向10 [12] |
| **L1 小模型** | 需要语义理解但任务简单 | 意图分类、任务难度打分、目标澄清 | 判断"这是概念题还是练习" | 方向10 [1][2] |
| **L2 大模型** | L0/L1 失败或高不确定 | 生成候选计划、复杂拆解、修复 | 首次拆"高数" | 方向10 [5][6] |
| **abstain** | 高不确定/超预算/高风险 | 明确说"不确定"并请用户介入 | 目标自相矛盾 | 方向10 [6] |

**升级判据**：`plan_consistency_divergence`（k=2–3 次采样的分歧度）越大越该升级（方向10 [27]）；验证失败（RuleEngine 拒绝）→ 升级并回灌结构化批评（方向10 [20]）。

**输出层强制**（两层分工）：
- **语法层**：GCD（语法约束解码）保证 plan JSON 字段合法（方向10 [25]）。
- **语义层**：RuleEngine 查硬约束（方向10 [11][19]）。
- **分工**：语法层不保证业务规则，RuleEngine 不关心 JSON 格式。

### 4.2 M6 Router（路由的具体特征与形态）

> M6 是 RO-2 的 8 个模型之一；本节只描述"门控"相关设计。

**输入特征清单**（详见 RO-2 §4.6）：

| 全称中文名 | 字段名 | 类型 | 来源 |
|---|---|---|---|
| 目标模糊度 | `goal_ambiguity_score` | float 0–1 | 规则/小模型 |
| 规则覆盖标记 | `rule_coverage_flag` | bool | RuleEngine |
| 校验通过标记 | `validator_pass` | bool | RuleEngine |
| 计划一致性分歧度 | `plan_consistency_divergence` | float | k 次采样 |
| 相似成功方案数 | `log_similar_solved` | int | 历史检索 |
| 剩余预算 | `budget_remaining` | float | 系统 |
| 用户档位 | `user_tier` | enum | 系统 |

**路由决策树**（【工程】形态，方向来自文献）：

```
可形式化（目标明确、依赖/时限清晰） → L0（不调 LLM）
规则/模板已覆盖                     → L0
有相似历史成功方案                   → 检索复用（不调或 few-shot）
语义/生成任务且简单                  → L1（小模型）
验证失败 / 高分歧 / 复杂             → L2（大模型）
高不确定 且 超预算 / 高风险          → abstain
```

**输出**：`route ∈ {deterministic, small_llm, frontier_llm, abstain}` + `max_tokens` + `reason_code`。

**依据**：LLM 长程任务成功率低（方向10 [29][30][31]）；外部验证器 > 内部自省（方向10 [11][19]）；采样一致性分歧可作不确定信号（方向10 [27]）；语法约束解码保格式（方向10 [25]）；验证要步骤级（方向10 [16]）。

### 4.3 验证：GCD + 外部校验

**职责**：验证候选计划是否可用。设计原则：**外部验证优先，LLM 自省不得作为唯一校验**。

#### 4.3.1 两层验证

| 层 | 机制 | 保证什么 | 不保证什么 | 依据 |
|---|---|---|---|---|
| 语法层 | GCD（语法约束解码） | JSON 字段/结构 100% 合法 | 业务规则 | 方向10 [25] |
| 语义层 | RuleEngine（外部验证器） | 硬约束（每日上限、前置依赖、间隔…） | 格式 | 方向10 [11][19][20] |

#### 4.3.2 步骤级验证

- 对拆解/计划的**每一步**独立校验，而不是只看最终答案（方向10 [16][17]）。
- 失败输出**结构化批评**：`violations[{code, severity, message, fix_hint}]`，机器可读、按步骤分解（方向10 [20]）。
- 批评回灌后重生成；若仍失败 → 升级模型级别或 abstain（方向10 [20][6]）。

#### 4.3.3 结构化上下文注入（辅助 LLM）

- prompt 带：User State、规则 schema、工具结果、历史成功计划（方向10 [8][9][10][13][15][20]）。
- 要求模型引用工具输出（Grounding），不凭空断言（方向10 [9][10]）。
- 执行反馈沉淀为记忆/技能库，相似目标先检索复用（方向10 [13][14][22]）。

### 4.4 降级路径

| 场景 | 降级动作 | 依据 |
|---|---|---|
| L2 失败 / 超预算 | → L1（小模型） | 方向10 [1][2][5] |
| L1 仍失败 / 预算耗尽 | → L0（规则/模板）+ abstain | 方向10 [1][2][12][6] |
| 分歧度无法获得 | 默认 L1 | 【工程】 |
| 高不确定 | 宁可 abstain，不硬编 | 方向10 [6][5] |
| 组件级故障（LLM 不可用） | 全程走 L0 确定性路径；M5 重规划降级为规则触发 | 方向10 [1][2][3]；RO-2 §4.11 |

**上线纪律**：学习型路由器上线前须离线 mini-benchmark ≥200 样本且"同通过率省成本 ≥20%"；任何模型/策略上线前离线回测 + shadow 至少 14 天（方向10 [4]；14 天为【工程】）。

### 4.5 成本优化

| 手段 | 做法 | 依据 |
|---|---|---|
| 能确定性求解就不调 | 可形式化目标走规则/求解器 | 方向10 [12] |
| 能复用就不调 | 相似历史成功计划检索复用 | 方向10 [13][14] |
| 任务级路由 | 简单任务走小模型/规则，复杂才升级 | 方向10 [1][2][3][4] |
| 级联 + 阈值 | 小模型先试，校验不过再升级；阈值离线调优 | 方向10 [1][2][5] |
| 早期弃答 | 高不确定早停，省下半程成本 | 方向10 [6] |
| 提示调度 | 分布式提示调度减少算力浪费 | 方向10 [7] |
| 成本监控 | 按任务类型记录调用量/成本/质量，先离线验证"路由是否划算" | 方向10 [4][7][27][28] |
| 不做 MoA | 多模型堆叠成本极高，与省钱目标相反 | 方向10 [28] |
| 不微调大模型 | 成本高、迭代慢；先用结构化 Harness | 方向10 小结 |

**砍预算顺序**：先砍"可形式化/规则可覆盖"的调用 → 再砍"有相似历史成功计划可复用"的调用 → 最后才对语义任务做任务级路由与级联（方向10 [1][2][3][12][13][14]）。

### 4.6 预期管理

- 长程 Agent 成功率本就低（方向10 [29][30][31]）；指标别设成 100%，给用户"可能失败"的预期，关键步骤人工兜底。
- 更强/更贵的模型也不能免除校验（方向10 [18][19][20]）：模型升级只降低调用频率，不取消校验。
