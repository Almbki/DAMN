## 3. CAT assessment flow

### Backend (implemented + tested)

New endpoints:

```text
POST /api/v1/users/me/trait-assessment/start          (idempotent resume; ?restart=true)
GET  /api/v1/users/me/trait-assessment/{id}
POST /api/v1/users/me/trait-assessment/{id}/answer    { item_id, response: 1..5 }
```

New table `trait_assessments` stores only the minimal resumable state:

* ordered `responses: [{item_id, response}]`
* `rr_index` (the CAT round-robin cursor)
* `unavailable` item ids
* `current_item_id`, `status`, timestamps
* artifact/model/feature versions + hash

Posterior/theta/SE arrays are **not** stored; `Level1Runtime` rebuilds them by
replaying responses in administered order. The model maths (GRM, EAP, Fisher
information, stopping) remains exclusively in
`app/user_models/level1/cat.py`.

Item text comes from the real `item_mapping.json` (`text` Chinese primary,
`text_en` secondary). The client submits raw 1–5 responses; no reverse scoring
or CAT logic exists in TypeScript.

### Frontend (implemented)

* Entry from Profile when `trait == null`: **完成初始画像**.
* The page calls `start` on mount, so refresh/reload resumes the same session.
* Questions are shown one at a time with 1–5 labels.
* Soft progress shows answered count, estimated remaining range, and current
  dimension. It never shows theta/SE/Fisher/GRM.
* Completion shows Big Five relative bands + uncertainty, with a collapsed
  “技术详情” section (theta, SE, CI95, items, model version).
* “重新测评” calls `start?restart=true`; the old session is retained as
  `abandoned`.

## 5. Task execution data collection

`TaskDetailSheet` now supports:

1. **开始任务** → `PATCH { started_at }` (backend records a partial
   `TaskExecution`).
2. **部分完成** → `PATCH { completed: false, completion_rate: 0.25|0.5|0.75,
   actual_duration, finished_at }`.
3. **完成任务** → `PATCH { completed: true, actual_duration, finished_at }`.

Actual minutes are prefilled from the task estimate and editable; they are sent
rounded to whole minutes. Completing from the list row still records a
`finished_at` but no actual duration (the sheet is the high-fidelity path).

Interruptions: **not implemented** — the backend API has no interruption field
on `TaskUpdateRequest`/`TaskRead`; Level 2 currently hard-codes
`interruption_count=0`. Adding it requires a schema/migration decision, so it
remains future work.

## 6. Feedback → Level 2 refresh

After a feedback submission is persisted:

1. Backend refreshes Level 2 (`UserModelService.refresh_dynamic_state`) during
   the feedback request.
2. Frontend calls `useProfile().refresh()` and `usePlan().refresh()` after the
   submission succeeds.
3. Existing replan job/SSE adoption continues unchanged.
4. If Level 2 is still unavailable, Profile shows the explicit empty state; it
   does not pretend the update succeeded.

## 7. Level 3 shadow isolation

* No ordinary user page reads `shadow_predictions`, Level 3 completion
  probability, disagreement, or success rate.
* `completion_probability` is only rendered when non-null; no fake `0%`.
* `prediction_source`/`prediction_mode` are mapped but only shown as a
  user-friendly “计划依据” (e.g. “任务估算”). Raw
  `deterministic:workload_estimate` / `shadow` strings are not shown in rows.
* The Developer page is the only place that displays raw model/artifact/shadow
  values.
* Level 3 remains shadow-only; `active` is still downgraded to shadow by the
  backend.

## 12. Remaining UX/data risks

1. **No browser automation / manual click-through** for the new assessment and
   profile screens; API smoke + typecheck + export only.
2. **Interruptions are not captured** (no API field). Level 2 receives
   `interruption_count=0`.
3. **Start time is local to the open sheet.** `TaskRead` does not expose
   `started_at`, so after a reload the UI cannot show an in-progress start time;
   the user can still enter actual minutes manually.
4. **CAT restart has no confirmation dialog.** It uses `?restart=true` and
   abandons the active session; a confirmation step would reduce accidental
   resets.
5. **Level 2 requires a Level 1 profile.** Without a completed CAT, feedback
   cannot populate dynamic state; the UI explicitly links back to assessment.
6. **Preview does not display completion probability.** This is intentional
   while Level 3 is shadow-only; no fabricated value is shown.
7. **Developer page is not role-gated.** It is only linked in API mode under
   Settings and is intentionally a dev/demo surface; production would need an
   environment flag or admin role.
8. **Real shadow statistics are not enough runtime data.** The developer page
   shows actual rows when they exist; no production success/disagreement
   numbers are asserted in this report.
9. **Mock mode still exists** and is marked `DEMO`; API mode remains the
   production path. It was not removed to preserve the demo flow.
10. **Legacy `UserStateRead` fields remain in the wire type** for compatibility;
    they are not rendered as the real profile state.
