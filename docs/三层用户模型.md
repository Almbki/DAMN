# 三层用户模型

> 这页是**目标设计**，不是当前代码。当前代码 `V1.1-test` 已经把 Level 1/2 真实运行时接进 `app/user_models/`，Level 3 只跑 shadow；具体现状见 [当前实现.md](当前实现.md)。`models_test/` 是冻结的测试/参考包，不是运行时依赖。

`models_test/` 是另一位成员的测试与参考实现，用来说明三层用户模型怎么工作。真实模型运行在 `app/user_models/`；`models_test/` 只保留 schema、测试和文档，不作为运行时依赖。

## 一句话

它测结果，我们定行动。

- 它回答：这个任务大概率能不能完成、实际要花多久。
- 我们回答：今天做哪几个、每个做多久、装不下怎么办。

它是测量和预测层，我们是决策层。两者是上下游，不冲突。

## 三层分别做什么

### 第一层：稳定特质

回答“这个人大体上是什么样”，不回答“今天怎么样”。

- 输入：120 道人格题，回答 1–5；按自适应方式选题，不是 120 题全做。
- 模型：五个维度分别做题目参数标定，再用贝叶斯估计；每个维度最少 4 题、最多 12 题，目标标准误约 0.35。
- 输出：五个维度的分数、标准误、95% 区间、每个维度答了几题。
- 验证：619,150 个官方样本；与完整题库相关 0.956–0.971；平均误差 0.198；平均 10.33 题/维度。
- 边界：不输出人格标签、自然语言人格描述、排程建议、任务完成概率；已经冻结，只读。

**我们怎么用**：作为首次画像，约 40–50 题，一次完成；允许跳过，跳过时标记特质缺失。它不是每天问。

### 第二层：每日状态

回答“今天累不累、压力大不大、有没有信心”，不回答“这个人是什么样”，也不直接回答“这个任务会怎样”。

- 输入：任务计划、任务执行、每晚反思（四段文字，可选）、第一层特质（只读上下文）。
- 模型：疲劳、压力、自我效能三个 0–1 状态；先按前一天做先验，再用当天反思证据和完成情况做贝叶斯校正。
- 行为指标：开始情况、坚持情况、完成比例、拖延证据；行为指标和状态分开，不混成一个“自律分数”。
- 边界：晚开始只是“可能拖延”，不是确认拖延；只有用户明确说“我主动拖延/逃避”才算确认；外部打断、生病、任务难度、计划变化不算拖延。
- 验证：54 个测试、13 项机器检查；结构和契约完成；没有大规模真实长期数据的预测有效性声明。

**我们怎么用**：每日状态进入第三层作为任务前状态；也可以给排任务提供“今天状态”的参考。四段反思都是可选的，不强迫每天写；没有写时，状态模型只靠任务记录，并标记证据不足。

### 第三层：单任务预测

回答“这个任务大概率能不能完成、实际要多久”。

- 输入：第一层特质、第二层任务前状态、任务本身、上下文、真实历史。
- 输出：完成概率（可能为空）、预测用时、预测模式、数据支持、快照 id、来源版本。
- 三种模式：冷启动（用时等于估计，完成概率为空，不编数字）→ 历史基线（完成率平滑 + 实际/估计用时中位数）→ 学习模型（数据过门槛才启用）。
- 边界：学习模型当前是空实现，没有训练；真正能用的是冷启动和历史基线；预测不等于排程。
- 防泄漏：预测前冻结快照；只用任务前状态；不用未来历史；不回填。

**我们怎么用**：目标设计是把预测用时作为排任务的输入；**当前代码不是这样**。当前生产用时来自确定性估计器，Level 3 只写 `shadow_predictions`，不控制排程；排程用 `predicted_duration or estimated_duration`，完成概率为空时按 1.0 处理。学习模型保持关闭。详见 [当前实现.md](当前实现.md) §5。

## 为什么不能直接拿它的代码跑

不是理念冲突，是接口和数据不配套：

- 它有自己的输入结构（任务计划、任务执行、反思、特质、状态、历史）；我们有自己的任务、执行记录和数据库。
- 它需要稳定特质和任务前状态；第一层可以接，第二层要每天更新；没有更新时只能标记缺失。
- 它只输出预测，不输出计划；排程仍由我们的规则做。
- 学习模型没训练；真正能用的只有冷启动和历史基线。
- 它用 JSON 存历史；我们用数据库。
- 它的测试是合成的；没有真实长期数据，不能声称预测准确。

这些不需要“映射层”：目标设计直接把它的字段当成 schema 基线，自己实现。当前代码的 `Task` 字段与它不完全一致（例如产品实体是 `Task.start_time`，DDSR 输入是 `planned_start`），差距见 [当前实现.md](当前实现.md)。我们的拆解和排程还需要一些它没有的字段（完成标准、前置任务、价值、任务类型、拆分单位、锁定），这些字段加在同一张任务上；这是超集，不是映射。

## 已经确定的接入方式

- 第一层、第二层、第三层都接；学习模型不接；不把模型历史存成 JSON 文件；它的排程代码不接。
- 当前运行时：Level 1/2 真实接入，Level 3 只 shadow；生产排程不读 Level 3。
- 第二层的反思用大模型抽证据，规则兜底；反思文本可能含隐私，需要脱敏、保留期、删除/导出和危机提示。
- 第二层的四段反思可选；目标设计是四段，当前生产 API 只接 `free_text`/`delay_reason` 合成的一个 `day_review`，差距见 [当前实现.md](当前实现.md)。
- `TaskPlan.planned_start` 是 DDSR 输入模型的必填；产品实体 `Task.start_time` 可空。当前代码在缺失时用默认 8:00；目标设计需要定一个默认开始时间。

## 我们真正能用的部分

- 冷启动纪律：没有数据就不编概率；用时先按估计。
- 历史基线：用历史完成率平滑出概率；用“实际用时 ÷ 估计用时”的中位数修正用时。
- 快照防泄漏：预测前冻结输入，结果单独记录，不回填。
- 状态/行为分离：不把晚开始直接当拖延，不把行为指标当人格判断。

## 不能承诺的

- 不能承诺预测准确；没有真实长期数据。
- 不能承诺“已经懂你”；第一层/第二层/第三层都需要真实记录积累。
- 不能承诺学习模型可用；当前是空实现。
