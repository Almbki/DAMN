## 0. 背景：这个项目是什么

一个**反馈驱动的自适应任务规划器**（feedback-driven adaptive task planner）。它要解决的问题是：

> 普通的待办工具假设"人是稳定的"——今天排 3 小时，明天还是排 3 小时。但人的精力、压力、可支配时间每天都在变，于是计划很快失效，用户放弃。

本系统试图让计划**对人的状态波动免疫**。它的一条完整链路是：

```
用户提出目标
  → 理论分析（这个目标该怎么拆）
  → 用户情境分析（这个人当前是什么状态）
  → 计划生成（产出一份任务清单与排期）
  → 硬约束校验（一票否决违规的计划）
  → 排程（在合法方案里挑最优顺序）
  → 执行
  → 反馈采集
  → 重规划（跑偏了就调整，且生成新版本）
```

**技术形态**：Python 3.12 + FastAPI 后端，LangGraph 编排计划生成流程，SQLAlchemy 2 + Alembic 管理数据，当前默认 SQLite。**本仓库只交付后端**；前端 App 由其他人开发（见 §4.2）。

## 3. 产品定位与成功判据

### 3.1 双价值主张（并列为主）

1. **拆解**：「不用自己想今天该做什么」——系统把模糊目标拆成一步可完成的任务。
2. **状态自适应**：「计划不会因为你状态崩了就作废」——系统随你的精力/压力/完成情况调整计划。

**次要支撑**：估时准确（"给你的时间估计是准的"）、知识不遗忘（复习调度，本期暂缓）。

> 依据：访谈第十四轮确认 `ab>cd`——**a/b 为主，c/d 为次**。

### 3.2 "自适应"的优先级（顺序有后果）

```
a 用户状态（精力/压力/疲劳）  >  c 完成率（跑偏就重排）  >  b 执行偏差（估时校准）  >  d 知识遗忘（复习排程）
```

> 依据：访谈确认 `acbd`。**注意 c 在 b 之前**——这意味着「反馈闭环/重规划」的开发优先级高于「估时模型」，本条直接决定 §9 的依赖链顺序。

### 3.3 交付判据

**「自己 / 小范围能真实用起来」**，不设硬性量化指标（访谈第十四轮确认：指标当前不清楚）。

这意味着：任何一个功能，如果它不能让人**真实地用一遍**，就不算完成。§9 的"验收判据"列按此精神写。

### 3.4 运行形态

- **按生产标准设计，但运行规模小**（自己 + 少量真实用户），不做多租户/并发扩容/灰度（见 §8 非目标）。
- **本仓库只交付后端**。0 层系统边界的外部实体见 §4。
- 已知约束：`docs/research/研究状态.md:271` 的决策 D26 规定「**禁止无对照全量上线自适应**」——即任何自适应策略上线都必须带实验开关。

### 5.3 计划的时间语义

| 决策 | 内容 | 理由 |
|---|---|---|
| **覆盖范围** | 一个计划版本覆盖一个**时间窗**（`plans.start_date` / `plans.end_date`），窗口内可含**多个目标** | `plans` 表**没有 `goal_id`**；目标关联只在 `tasks.goal_id`（`app/infrastructure/database/models/task.py:39`）。一个目标一份计划需要重构表结构，而现状已天然支持多目标 |
| **版本生命周期** | **事件驱动**：只有 ① 反馈触发重规划、② 用户手动重规划 才产生 `v(n+1)`；其余时间只更新任务状态与排期 | 不引入定时任务基础设施；与"版本不可变 + `parent_plan_id` 链"契合 |
| **局部修复幅度** | `local_repair` **只改未来 2 天**；`30%` 是 `full_replan` 的**幅度闸门**（单次改动任务超过 30% 时降级为局部修复） | 数值沿用 `docs/research/RO-5-RuleEngine与决策架构.md:202`（"只改未来2天 ≤30%"）与 `:132` 的 R12 |
| **默认时间窗** | 当前代码在用户未给日期时硬编码 `start + 13 天`（`app/api/v1/plans.py:41`）——**这是一个隐式默认，属于缺口** | 见 §6.1 澄清流程 |

## 6. 功能需求

### 6.1 目标与拆解流程

**流程**（访谈第十二轮确认）：

```
用户点"添加目标/任务"
  → 自动进入拆解流程（用户可随时取消）
  → 展示【草案预览】
  → 用户在编辑草案的同时，可与 AI 对话进行澄清
  → 确认
  → 落库（过 RuleEngine 校验）并生成排期
```

**子决策**：

| 决策 | 内容 |
|---|---|
| 拆解方式 | **人机协作**：系统出草案，用户可增删改任务、调整拆分粒度，确认后才落库 |
| 对话编辑形态 | **AI 生成改动清单（diff），用户确认后才生效**——不做"AI 直接改库" |
| 权限边界 | **草案阶段可自由编辑**；**已落库计划的排期不可由用户直接修改**（见 §6.6） |
| 取消后 | 目标**保存为草稿**，不丢弃 |
| 目标进度算法 | **按预估时长加权**：`Σ(已完成任务 estimated_duration) ÷ Σ(全部任务 estimated_duration)` |

**理由摘录**：草案审核不影响硬约束的权威性（草案尚未过 `RuleEngine`）；进度按条数算会被"任务粒度"污染（把一个大任务拆成 10 个小任务，进度条会跳变），而任务粒度正是系统在动态调整的东西。

**需新增**：`GoalStatus.DRAFT`（当前 `app/domain/models/enums.py:16-20` 无此取值）→ 标注 `与实现冲突`。

### 6.2 计划生成

沿用现有 LangGraph 六节点流程（`app/agent/graph.py:230-240`）：

```
goal_analysis → theoretical_analysis → user_situation_analysis
  → plan_generation → rule_validation ⇄ plan_repair
```

- **校验-修复循环**：`rule_validation` 后接条件边，由 `_should_repair`（`app/agent/graph.py:202-208`）判断——"必须有违规、且重试预算未用完"才继续修；`plan_repair` 回边到 `rule_validation`（`app/agent/graph.py:240`）。默认预算 `max_repair_attempts=2`（`app/agent/graph.py:364`）。
- **代价是真实的**：每命中一次硬规则 = 一轮"重新生成计划 → 重新校验"，最多两轮。这就是为什么"证据强度不足的规则不应做成 hard"（见附录 A）。
- **生成过程对前端可见**：事件经 SSE 回放（`app/api/v1/plans.py:119`、`app/application/services/generation_service.py:58`）。

| **软规则** | 注意：`ViolationSeverity.SOFT` 有定义（`app/domain/models/enums.py:68`）但**全仓库没有任何规则使用它，也没有消费者**——`RuleEngine.hard_violations()`（`app/domain/rules/base.py:122-125`）只过滤 hard。因此"做成 soft"目前等于写入一个没人读的字段 |

**新增规则须遵守**：在 `default_rules()` 注册时通过"同输入无相反动作"一致性检查（`docs/research/RO-5-RuleEngine与决策架构.md:148` 的 D19）。

### 6.4 执行与番茄钟

**决策：内置专注计时，完整形态但"不固定、不强制"。**

| 项 | 决策 |
|---|---|
| 计时方式 | **正计时 + 可配置倒计时并存**；倒计时可配置**时长**与**轮数**（工作多久 / 休息多久） |
| 强制性 | 到点**只提醒**，不锁界面、不自动开始休息 |
| 收尾状态 | 四态：`completed` / `paused` / `abandoned` / `interrupted` |
| 数据归宿 | **新增"专注会话"实体**（一个任务对多段会话），而非只累加到现有字段 |

**为什么必须新增实体**（这是本节的关键论证）：
现有 `task_executions`（`app/infrastructure/database/models/execution.py:21`）对一个任务只记 `planned_duration` / `actual_duration` **各一个数字**外加起止时间戳——等于假设"一个任务 = 一段时间连续做完"。现实是一个任务常横跨多段（上午 25 分钟被打断、下午又 40 分钟），**"被打断了几次""每段什么时候做的"全部丢失**。

新增专注会话后，一次性补上三个**现在算不出来**的量：

1. **启动延迟**——计划开始时间 → 第一段会话真正开始的时间差。
   （`docs/research/RO-5-RuleEngine与决策架构.md:185` 的图二**明确要求派生**"启动延迟"，现有数据算不出）
2. **被打断次数**——`end_reason = interrupted` 的计数，是拖延与精力最直接的可观测代理。
3. **真实时段分布**——每段会话的 `started_at` 落在哪个时段，用于**推断**"主导时段"，从而不必再问用户（呼应 §6.5 的"能算就不问"）。

**建议字段**：`task_id` / `started_at` / `ended_at` / `planned_seconds` / `actual_seconds` / `round_index` / `end_reason`。

### 6.5 反馈采集

**决策：整体采用 `docs/research/RO-3-用户状态评估.md` 的设计。** 该文档已有完整设计，本节只做确认与补充。

| 项 | 设计 | 出处 |
|---|---|---|
| 注册问卷 | **12–15 题 / 4–5 分钟**，一次性 | `docs/research/RO-3-用户状态评估.md:23`、`:97-197` |
| 每日打卡 | **≤30 秒，3 题必答 + 1 题可选** | `:24`、`:199-209` |
| ├ D1 | 「现在的精力如何？」1–5 → `self_energy_vas` | `:205` |
| ├ D2 | 「现在的压力大吗？」1–5 → `self_stress_now` | `:206` |
| ├ D3 | 「今天大概能投入多少时间？」<30 / 30–60 / 60–120 / >120 → `self_today_budget_min` | `:207` |
| ├ D4（可选） | 「昨晚睡了多久？」**每周 3 次** → `log_sleep_hours` | `:208` |
| └ 系统自动 | 答题反应时 → `log_questionnaire_rt_ms` | `:209` |
| 任务后反馈 | **1–2 题，且不每次都问**：T1 完成状态 / T2 费劲程度 1–5 / T3 卡点（**只在没做或部分完成时**）/ T4 重要性（可选） | `:213-220`、`:222` |

| 熔断 | 当日 >5 题或熔断激活 → 丢弃一切非必答题，**打卡降级为 1 题（仅精力自评）** | `:388` |
| 四级疲劳截断 | 跳过率 >40% → 降到 2 题；>60% → 暂停 7 天；反应时 > 中位数 2 倍；连续 3 次打开不答 → 暂停 14 天 | `:382-384` |
| 出题硬规则 | 禁止评价人格/质问；禁止医疗诊断、心理疾病、隐私敏感话题 | `:309`、`:313` |
| 与规则对齐 | 与 `docs/research/RO-5-RuleEngine与决策架构.md:133` 的 R13（提示 >3 次/天丢弃）、`:135` 的 R15（>5 题熔断）数字完全一致 | — |

**"能算就不问"原则**（`:380`、决策 D15 `:411`）：

> 慢的、稳定的、主观体验的**靠问**；快的、可观测的、行为副产物的**靠算**。

**被动行为信号的范围**（本期的关键决定）：

| 类别 | 信号 | 本期 |
|---|---|---|
| **(A) 后端自己就能算**（零客户端配合） | `log_completion_rate_7d`、`log_duration_ratio`、`log_first_action_delay_min`、`log_abandon_pattern`、`log_hour_success_dist`、`log_streak`、`log_reschedule_count`、`log_consecutive_high_cog` | **必须做** |
| **(B) 需前端埋点，本期做** | `log_questionnaire_rt_ms`、`log_rt_cv`、`log_night_activity`、`log_prompt_ignore_rate` | 做（依赖前端配合） |
| **(B) 需前端埋点，本期砍掉** | `log_typing_wpm`、`log_typing_error_rate`（打字动力学） | **不做** |

**砍掉打字动力学的理由**：它需要**持续键盘钩子**，而 RO-3 自己在 `:95` 把"**持续键盘内容**"列为隐私红线；且移动端无法实现。同一机制有一个更窄、更可解释的替代——答题反应时及其变异（RO-3 `:93` 正是用它作疲劳代理）。

**任务后归因的交互**（本期的关键决定）：RO-3 只规定"失败时问 T3 卡点"（`:219`），但 `blocker_type` 的选项枚举未定（未决 T-3.4，`:423`）。本期定案：

- **预选式**：系统按历史模式与本次信号**先勾中一个**，用户**确认或改**（一次点击）。
- **选项枚举（本版）**：`太难` / `没时间` / `不想做` / `被打断` / `忘了` / `其他`。
- 理由：预选把一道"思考题"降级成"确认题"，服务 RO-3 的"≤30 秒 / 疲劳预算"目标；而"完全由系统推断"不可行——`app/ml/` 下的 predictor 全是 `statistical-*` 占位，没有训练数据。

### 6.6 权限：用户能改什么

| 对象 | 用户可做 | 不可做 |
|---|---|---|
| **拆解草案** | 任意增删改任务、调整粒度、与 AI 对话 | — |
| **已落库计划的任务** | 改状态、记录实际执行数据、勾选完成判据 | **不能改排期、不能删除、不能新增** |
| **计划版本** | 触发手动重规划 | 不能直接编辑排期 |

**现状**：`app/api/v1/tasks.py:21` 只有一个端点 `PATCH /{plan_id}/tasks/{task_id}`；其载荷 `TaskUpdateRequest`（`app/schemas/task.py:50-62`）仅允许 `status` / `completed` / `actual_duration` / `difficulty_feedback` / `stress_before` / `stress_after` / `failure_reason` / `started_at` / `finished_at` / `standard_updates`。

**为什么不让用户改排期**：`app/domain/rules/base.py:7` 的注释原文是 "The rule engine is the *only* authority on hard constraints"。用户手拖任务会把计划拖进违规态，要么每次手改都触发一轮完整校验（复杂度与延迟上升），要么破坏不变量。

**未来增加（低优先级）**："锁定"语义——把某些任务钉死（`is_flexible = False`），重规划不许动它。**基础设施已全部存在**：字段 `app/domain/models/task.py:32`、ORM 列 `app/infrastructure/database/models/task.py:67`、排程器消费点 `app/domain/scheduling/scheduler.py:170`，只差 API 载荷里加一个字段。

### 6.7 重规划与决策权

| 项 | 决策 |
|---|---|
| 决策权 | **全自动**（保持现状）：提交反馈时若完成率低于阈值，系统**直接**生成 `v(n+1)` 并落库 |
| 阈值 | `completion_rate < 0.5`，`app/application/services/feedback_service.py:18`、`:47` |
| 冷却 | **per-user** 48 小时（不是 per-plan），`app/application/services/replan_service.py:60`；命中返回 409 |
| 补强要求（本期新增） | **可解释 + 可撤销**：每次自动重规划必须写明**触发原因**与**改了哪些任务**；用户可一键回退到上一版 |

**为什么强调可解释**：`replan_events` 表已有 `trigger_type` / `reason` / `changed_tasks`（`app/infrastructure/database/models/replan_event.py:20`），但**只写不读**——用户完全不知道系统动过他的计划。数据已经在，缺的只是展示。

**可撤销为什么成本低**：计划版本不可变 + `plans.parent_plan_id` 已串起版本链，回退是纯读操作。

**为什么不做"半自动（用户确认后才落库）"**：价值主张 b「计划不会因为状态崩了就作废」**正是靠全自动兑现的**；改成半自动，这句主张就退化成"系统会提醒你手动改计划"。另外现有集成测试 `tests/integration/test_plan_flow.py` 正依赖这个自动行为。

### 6.8 洞察与画像

**⑤ 数据洞察面板 = 闭环归因**（不只是报表）：

现有 `InsightService.get_insights`（`app/application/services/insight_service.py:28-92`）已能产出：总任务数 / 完成数 / 完成率、计划与实际总时长、平均压力、平均精力、高认知分钟数、`predicted_vs_actual_ratio`（实际÷计划比，`:70-72`）、认知负荷分布、按天完成度序列、以及 4 条规则化建议（`:94-109`）。

**但"执行数据 → 用户模型更新"这条回环是断的**：`app/application/services/user_model_service.py:38` 的 `update_model` **没有任何调用方**；`_recommendations` 输出的建议**只是返回给 API 的字符串，没有任何系统部件消费**。

**本期要求**：把洞察的数字（`predicted_vs_actual_ratio`、完成率、平均压力）**回写进 `user_models`**，接上这条断链。这是"执行偏差 → 估时校准"唯一可行的物理载体。

**画像页（前端，一级页）展示三级**：

1. 当前状态（精力 / 压力 / 效能）
2. 趋势曲线（近 7 / 30 天）
3. **数据充足度**（`user_models.sample_size`）与**系统依据**（这个判断怎么来的、被哪些规则用了）

**硬约束**：措辞**不得含人格评价关键词**（R14，`docs/research/RO-5-RuleEngine与决策架构.md:134`）。画像页只呈现**状态**，不呈现**评判**。

### 6.9 提醒与集成（低优先级）

**决策**：后端只做**决策**，前端负责**投递**。

- 后端产出「该不该提醒、提醒什么、为什么」：`{should_remind, 文案, 关联任务, 决策理由, 有效期, 幂等ID}`，通过**只读查询接口**（如 `GET /api/v1/reminders/pending`）由前端轮询。
- **文案由后端给**：R14「反馈指向检查」必须在文案出门前跑一遍（`docs/research/RO-5-RuleEngine与决策架构.md:134`）。
- **不做**：长连接主动推送（现有 SSE 是**事件回放**语义，`app/application/services/generation_service.py:58`，改造成实时总线属于另一个量级）、日历双向同步。

### 6.10 设置

**决策**：账号信息 + **排程偏好持久化**。

**缺口**：`PlanGenerateRequest`（`app/api/v1/plans.py:60-69`）有一套排程旋钮——`available_minutes_per_day` / `daily_limit_minutes` / `buffer_minutes` / `high_cognitive_max_per_day` / `execution_weight` / `user_profile`，但**每次生成都要重传**；`users` 表只持久化了 `execution_weight` 与 `profile` JSON（`app/infrastructure/database/models/user.py:23`）。"我工作日只有 2 小时"是**长期事实**，不该每次重填。

### 6.11 首次使用

**决策**：一次引导——**填基础档案 → 建第一个目标 → 生成第一份计划**。

- 基础档案即 RO-3 §4.2 的注册问卷（`docs/research/RO-3-用户状态评估.md:97-197`）。
- 理由：系统需要**冷启动输入**（每日可投入时间等）才能产出像样的第一份计划；"第一次就给我一份烂计划"对自适应类产品是致命的。
- 顺带作用：把 §6.10 的排程偏好持久化变成**首次使用时的必填**。

## 附录 A：文献核查——为什么 R1 被降级

**背景**：`docs/research/RO-5-RuleEngine与决策架构.md` 把 R1「远端目标必配近端子目标」列为 **15 条 P0 硬规则的第 1 条**，依据是卡片 `方向3 [4]`（Bandura & Schunk 1981）与 `[5]`（Latham & Seijts 1999）。

**一次独立文献核查的结论**（核查过程见下）：

| 主张 | 结论 | 说明 |
|---|---|---|
| 远端目标需配近端子目标 | **混合（mixed）** | 方向有支持，但"**必须**配对"过强 |
| 任务须为一步可完成的原子单元（GTD 语义） | **弱（weak）** | 属从业者经验法则，无直接实证 |

**三条反证**：

1. **原始研究没有被正式重复，也没有专门的元分析。** Bandura & Schunk (1981) 被引 2000+ 次，但原始研究 **N=40、数学落后儿童、结构化算术任务**。这是"广泛引用、直接证据薄"的典型。
2. **直接被反驳**：Seijts & Latham (2001) 在需要学习的复杂任务上发现，「远端学习目标 **+** 近端结果目标」**并未**优于「单独的远端学习目标」。**值得注意的是，这正是 `RO-5` 卡片 `方向3 [6]` 自己引用的那篇**（`docs/research/03-任务拆解/papers.md:226`）。
3. **子目标增殖有负向区间（支持较强）**：Fishbach, Dhar & Zhang (2006) 发现达成一个子目标会让人把后续行动当作**替代品**（licensing 效应，反而减少投入）；Huang, Jin & Zhang (2017) 发现子目标结构**在追求初期提升动机、在接近完成时反而降低**动机。

**一条方法论纠正**：把"目标接近性"当作 Locke & Latham 目标设定理论的结论是**误引**——该理论的核心是**具体性与难度**（元分析 Mento et al. 1987；难度效应量 d≈0.52–0.82），"接近性"是另一条更弱的、由 Bandura 系研究主导的支线。

**本项目的取舍**：

- 文献支持「**近处应该有能完成的东西**」这个**方向** → 所以**不删除**这个意图，而是改为 **Scheduler 默认排程行为**（与 `docs/research/RO-5-RuleEngine与决策架构.md:137` 已有的先例一致：R6/R7/R11/R18 等候选规则"由 Scheduler / Plan Generation 默认行为承担"）。
- 文献**不支持**「远端目标**必须**配近端子目标」成为**一票否决的硬规则** → 因为 hard 的代价是真实的：每次命中都要 **reject + 回灌 + 重新生成**，最多两轮（`app/agent/graph.py:202-208`、`:235-241`）。用一个 mixed 证据行使一票否决权，成本与证据强度严重不成比例。

**引用（均已核实存在）**：

1. Bandura, A., & Schunk, D. H. (1981). *JPSP*, 41(3), 586–598. DOI `10.1037/0022-3514.41.3.586`
2. Latham, G. P., & Seijts, G. H. (1999). *JOB*, 20(4), 421–429.
3. Seijts, G. H., & Latham, G. P. (2001). *JOB*, 22(3), 291–307. DOI `10.1002/job.70`
4. Locke, E. A., & Latham, G. P. (2002). *American Psychologist*, 57(9), 705–717.
5. Mento, A. J., Steel, R. P., & Karren, R. J. (1987). *OBHDP*, 39(1), 52–83.
6. Wood, R. E., Mento, A. J., & Locke, E. A. (1987). *JAP*, 72, 416–425.
