# 第一部分：真·流式传输系统

## 1.1 先说结论：现在到底“流”在哪

以前的问题是：

- `POST /plans/preview`、`/adjust` 已经是“后台线程 + 实时 SSE”；
- 但 `POST /plans/generate` **表面返回 202，实际在请求线程里把整条流水线跑完**，SSE 只是事后回放；
- `POST /plans/{id}/replan`、`POST /plans/decompose` 完全同步，没有 job、没有 SSE；
- 反馈触发的重排也在反馈请求里同步执行。

现在改成：

| 能力 | 现在 |
| --- | --- |
| `POST /plans/generate` | **立即 202**，后台线程跑图，节点完成即推 SSE，最后 `completed` 帧带完整 plan |
| `POST /plans/preview` | 保持真异步 job（原有能力） |
| `POST /plans/preview/{id}/adjust` | 保持真异步 job（原有能力） |
| `POST /plans/decompose` | **立即 202 job**，结果（按天草稿）在 job 的 `completed` 帧里 |
| `POST /plans/{id}/replan` | **立即 202 job**，结果（新版本信息）在 `completed` 帧里；冷却不满足仍立刻 409 |
| `POST /plans/{id}/feedback?stream_replan=true` | 反馈先落库，重排图作为 job 流式执行；响应多一个 `replan_job_id` |
| 两个 `confirm` | 保持同步（只是落库，很快，且需要原子性） |

> **粒度说明**：本次是**节点级实时流**（每个 LangGraph 节点开始/完成就推送），
> 不是 LLM token 级。原因：默认流程是确定性启发式，LLM 默认是 mock；token 流需要把
> 同步架构改成 async，成本高且当前收益低。token 级可以作为下一阶段。

## 1.2 流式架构（谁在推、谁在收）

```
浏览器/前端
  │ 1) POST /plans/generate
  ▼
FastAPI 路由 (app/api/v1/plans.py:204)
  │ 2) 立即返回 202 {job_id, status:"running", events_url, status_url}
  │    同时 GenerationService.submit() 起一个 daemon 线程
  ▼
GenerationService (app/application/services/generation_service.py:62 submit)
  │ 3) 后台线程 _run_job (:164) 自己 new 一个 PlanService（自己的 DB session）
  ▼
PlanService.generate_plan_with_events (plan_service.py:418)
  │ 4) 跑 Graph A（preview）→ confirm（resume）→ 落库
  │    每个节点 ctx.publish("node.started"/"node.completed")
  │    _run() 把事件同步镜像给外部 emit
  ▼
GenerationJob.events（内存环形/追加列表）
  ▲                    │
  │ 5) notify_all      │ 6) SSE 订阅
  │                    ▼
前端 GET /plans/generation/{job_id}/events
  → stream_sse() 先回放已有事件，再 wait(15s) 等新事件，最终发 completed
```

关键点：

- **事件是真的在节点执行时产生的**，不是跑完后“编”的。节点里已经有
  `ctx.publish(...)`（见 `app/agent/state.py:100`）。
- `PlanService._run`（`plan_service.py:218`）在调用图时同时写两份：
  内部 `RunEvents`（用于 trace/审计）和外部 `emit`（用于 SSE）。
- `GenerationService._run_job`（`generation_service.py:164`）现在在**锁内**写
  `job.result / job.plan_id / job.status` 并 `notify_all()`，保证 `completed` 帧一定带结果。
- **晚订阅不丢历史**：`stream_sse` 先回放 `job.events`，再等新事件。
- **心跳**：15 秒没事件发 `: ping`，防代理断开。
- **TTL**：job 在内存里保留 `GENERATION_JOB_TTL_SECONDS`（默认 1800 秒）。

> ⚠️ 多进程部署注意：job 注册表是**进程内存**。如果 uvicorn 开多个 worker，
> 提交 job 的 worker 和处理 SSE 的 worker 可能不是同一个。要么 sticky session，
> 要么后续把 job 状态放到 Redis/DB。

## 1.3 一次“真流式生成”的完整时序

以 `POST /plans/generate` 为例：

```
前端                          后端
 │ POST /plans/generate        │
 │────────────────────────────>│
 │<────────────────────────────│ 202 {job_id, status:"running", events_url, status_url}
 │                             │
 │ GET {events_url}            │  GenerationService.submit 已启动后台线程
 │────────────────────────────>│
 │<── event: agent.started ────│
 │<── event: load_context ─────│  data.event = node.started / node.completed
 │<── event: classify_request ─│
 │<── event: goal_analysis ────│
 │<── event: theoretical_analysis
 │<── event: user_situation_analysis
 │<── event: plan_generation ──│
 │<── event: rule_validation ──│  （有硬违规会看到 plan_repair 循环）
 │<── event: preview ──────────│  图 A 在此暂停（interrupt）
 │<── event: agent.completed ──│
 │<── event: agent.started ────│  自动 confirm：resume 图 A
 │<── event: plan_finalization │
 │<── event: agent.completed ──│
 │<── event: completed ────────│  data: {job_id,status,result:{plan_id, plan}}
 │                             │
```

> 每个节点会发 **started 和 completed 两条**，SSE 的 `event:` 名都是**节点名**；
> 用 `data.event` 区分是 started 还是 completed。这是为了让前端可以稳定地按节点名监听。

重排（`POST /plans/{id}/replan`）的时序：

```
event: replanning.started
event: load_context
event: process_feedback
event: ml.started / ml.completed        (ml_prediction 节点)
event: adjustment_router
   ├─ MICRO_ADJUST → event: micro_adjustment → event: rule_validation ...
   └─ FULL_REPLAN  → event: goal_analysis → theoretical_analysis
                     → user_situation_analysis → plan_generation
                     → rule_validation（→ plan_repair 循环）→ new_plan
event: replanning.completed
event: completed                        (result = ReplanResponse)
```

反馈流式重排（`?stream_replan=true`）同理，只是以 `agent.started` 开头，
最后 `completed` 的 result 是 `{replan_triggered, replan_plan_id}`。

## 1.4 SSE 事件契约（前端按这个写）

| `event:` 名 | 什么时候出现 | `data` 里有什么 |
| --- | --- | --- |
| `<节点名>` | 节点 started/completed（如 `goal_analysis`、`plan_generation`） | `event`(node.started/node.completed)、`node`、`stage`、`summary`、`payload` |
| `tool.completed` | 工具调用结束 | `tool`、`ok` |
| `ml.started` / `ml.completed` | 预测节点 | `route`、`source` |
| `preview.generated` | preview 节点产出草稿 | `tasks`、`node` |
| `agent.started` / `agent.completed` | 一次图运行开始/结束 | `run_id`、`graph` / `thread_id` |
| `replanning.started` / `replanning.completed` | 自动/手动重排 | `reason` / `run_id` |
| `completed` | **终态（成功）** | `job_id`、`status`、`result` |
| `failed` | **终态（失败）** | `job_id`、`status`、`error` |
| `: ping` | 15 秒无事件的心跳 | 无（注释行） |

节点名全集（会作为 `event:` 出现）：
`load_context`、`classify_request`、`goal_analysis`、`theoretical_analysis`、
`user_situation_analysis`、`plan_generation`、`rule_validation`、`plan_repair`、
`preview`、`plan_finalization`、`process_feedback`、`ml_prediction`、
`adjustment_router`、`micro_adjustment`、`new_plan`。

## 4.6 摘出时的 10 个坑（按重要性）

1. **应用层反向 new 应用服务**：`repo_context_builder.py:100-102`、`feedback_service.py:101-103`、`plan_service.py:940-943` 都 lazy import + new `ProfileService`。摘包时容易循环依赖，改成构造注入端口。

4. **纯函数契约**：`domain/profile` 只 import stdlib + 本包。迁移时**不能**引入 FastAPI/SQLAlchemy/Pydantic。
5. **degraded 语义分散**：`models.py:52`、`engine.py:165/183`、`profile_service.py:219`、`schemas/profile.py:57`。统一成一个常量/方法。
6. **`predict_duration/predict_completion/should_prompt` 生产未用**：只被 `tests/unit/test_profile.py` 调用；生产预测走 `app/ml/*`。重构时要明确“画像只产特征/先验，ML 产预测”。

8. **任意画像字段都会重置状态**：`upsert_profile` 收到任意画像字段就 `init_state`（`profile_service.py:108-110`），只改 `identity` 也会把 `update_count` 归零。确认产品语义。

10. **三种画像表示**：`profile_prompt_json`（`engine.py:296-317`）、`snapshot`（`profile_service.py:213-220`）、`ProfileRead`（`schemas/profile.py`）。字段集合不一致会导致 Agent/API/前端看到不同画像；建议收敛成单一 `PortraitSnapshot`。
